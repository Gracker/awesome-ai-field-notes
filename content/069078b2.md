## 原文摘录（claude.dev，2026-11-16）

On the Claude Code team, the vast majority of our code (~90%) is written and reviewed by Claude. Verification loops are the building block that lets you delegate more work to Claude. In internal testing around structured file generation, having a separate grader check Claude's work against a rubric improved task success by up to 10 points over a standard prompting loop, with the largest gains on the hardest problems.

### How the Claude Code team thinks about verification

- Verification means running the change: Claude Chrome extension for web changes, iOS or Android MCP for mobile, computer use for desktop, or run the service locally for backend work. Put verify skills in .claude/skills/ as close to the code as possible; invest in making them fast and reliable.
- Failing tests require human attention: Claude runs the checks and tries to fix anything that fails; if still failing after three rounds, it stops and brings in a human.
- Code owners write their own checks, refined until they flag what the owner would flag.
- One reviewer, multiple rounds: adding a second reviewer on top of the primary is often worse than tuning the primary; REVIEW.md says what to watch for, and each pass builds on earlier rounds' context instead of re-checking from scratch.
- Changes can't modify their own checks: Code Review reads REVIEW.md from the base or default branch, never from the PR's changes; reviews are reserved for commits; cheap checks run first (tests, build, linter before opening a PR).
- Turn misses into rules: extract patterns from human review comments and PR reverts, have three agents try to disprove them, human-approved via PR; replay three bug finders against PRs tied to known incidents. Flaky tests: no skipping, no sleeps, no retry-until-pass - root-cause or delete with a written reason.
