## 摘要

Android 应用建立在抽象核心 Android 系统功能的 API 之上。这些 API 被官方记录在随 Android 源代码或 SDK 分发的多个文件中，我们统称为 Android API 列表（Android API Lists，简称 AALs）。此前的 Android 研究依赖于特定的 AALs，通常将它们视为可互换的 ground truth（基准事实）。然而，最近的研究表明，不同的 AALs 可能导致截然不同的研究结论，这引发了人们对 Android 基于 API 分析的有效性和可重复性的担忧。为了解决这个问题，我们首次对先前工作中广泛使用的四种官方 AALs 进行了深入的实证研究。我们系统地刻画了它们的内容，并分析了它们在 Android 各版本中的演化。然后，我们对每个 AAL 中记录的 API 进行了细粒度比较，以揭示其底层的 API 包含策略和不一致性。为了评估这些差异的实际影响，我们进一步在九台 Android 设备（包括原版 Android 和厂商定制系统）上检查了 API 可用性。最后，我们分析了 17,759 个真实 Android 应用（包括开源应用、商业应用和恶意软件）中的 API 使用情况，以量化 AAL 的选择如何影响实证 Android 研究。我们的结果显示，官方 AALs 既不稳定也不相互一致，它们之间的差异可能显著影响研究结论。我们还观察到厂商定制 API 被正常应用积极使用，但现有研究在很大程度上忽略了这一点。基于这些发现，我们讨论了它们对 Android 基于 API 的研究的启示，并提供了可操作的建议，帮助研究人员更可靠地选择和解读 AALs。

## 1 引言

Android 框架提供了一组 API，这些 API 抽象了核心的 Android 系统功能和硬件特性，从而支持正在运行的应用程序的功能。这些 Android API 简化了应用开发，但它们也带来了 API 兼容性问题 [50]。已有研究表明，那些频繁变化的 Android API 可能引发更多开发者的讨论 [35]，甚至威胁到应用的评分 [34]。在用户端，人们可能会发现某个特定应用只能在特定的 Android 版本或设备上运行，导致糟糕的用户体验。Android SDK [11] 提供了一些工具来减少开发者在这种情况下的维护工作量。例如，AndroidX [29] 帮助维护 API 的向后兼容性。Lint [5] 是另一个 SDK 工具，提供基于规则的代码异味扫描服务。它可以检测应用源代码中的某些 API 兼容性问题 [24, 48]。然而，Lint 的性能已被证明是较弱的 [23, 48, 50, 52]。

这些兼容性问题引起了研究者的关注。Wei 等人 [50] 开发了 FicFinder，一种通过 API 及其各自触发问题的上下文对（即 API-context pairs）来识别兼容性问题的工具。然而，FicFinder 依赖于一组手动编写的 API-context pairs，限制了其在不断演化的 Android 生态系统中的实际可用性。后来的静态兼容性问题检测器大多包含一个独立的系统化 API 采集模块。例如，CiD [31] 有一个 API 生命周期建模模块。它读取 Android 框架的源代码并提取 API 的生命周期用于基于 API 的问题检测。IctApiFinder [22] 是另一个兼容性问题检测器，它收集 Android SDK 中捆绑的 android.jar 文件中的所有 API。Mahmud 等人提出了 ACID [39]，它利用 Android API 差异报告 [9] 来检测两种 API 兼容性问题。正如 Liu 等人 [37] 指出的，具有系统化 API 采集方法的工具可以检测到比不具有该方法的工具显著更多的问题。他们还发现，使用不同 API 知识来源的工具输出的重叠结果很少。

上述研究工作都依赖于特定的 Android API 知识。研究结果的准确性在很大程度上依赖于精心策划的 API 列表的使用。我们将此类精心策划的 API 文件称为 Android API 列表（简称 AALs）。尽管 AALs 在先前的工作中被广泛使用，但人们对它们是否忠实地代表了 Android API 知识知之甚少。事实上，我们揭示了即使在同一个 Android 版本中，不同的 AALs 可能记录了不同的 API 知识，而且 AAL 中记录的 API 可能不反映运行 Android 设备中的实际 API。例如，在 Android 13 中，四个 Java 方法被从 AAL current.txt 中移除，尽管它们仍然保留在 Android 框架中并且可以被正常应用使用。这个 AAL 被最先进的 API 兼容性问题检测器 PSDroid 所使用。不完整的 API 包含给 PSDroid 的检测结果带来了假阴性。换言之，不完整或不正确的 AALs 对各种研究结果构成了实质性威胁。

**我们的贡献：** 对 Android API 列表的更好理解可以帮助 Android 研究者和从业者在未来做出更明智的决策。为此，我们首次对六个 Android 发行版本下的四种官方 AALs 进行了深入研究。具体而言，我们研究了这些 AALs 如何从 Android 系统中包含 API、它们如何随着 Android 平台的演化而变化，以及它们彼此之间的差异。我们进一步探索了九台真实 Android 设备上的 API 存在性以及 17,759 个真实 Android 应用中的 API 使用情况。我们的研究揭示了四种官方 AALs 之间的 API 不稳定性和不一致性，以及它们对 Android 生态系统的影响。

我们的研究揭示了以下关键发现：

1. AALs 表现出显著的不一致性，在所有调查的 AALs 中只有少数（约10%）API 是共享的。
2. AALs 可能包含大量合成 API，这些 API 在某些 AALs 中存在，但在 Android 源代码或真实 Android 设备中不存在。
3. 没有单一的 AAL 能完全记录所有 API，特别是对于非 SDK 接口和厂商定制 API。
4. AALs 的 API 包含策略是不稳定的，会在平台演化过程中发生变化。

我们还强调了 Android API 领域的研究机会，特别是非 SDK API 和厂商定制 API。为了支持未来的工作，我们在 https://github.com/sqlab-sustech/AAL-artifacts 上发布了所有研究工件，包括 AAL 数据集、工具源代码和实验结果。

### 2.2 API 定义

Android 框架 API 是用 Java 编写的，这意味着它们要么是某些 Java 类的字段，要么是方法。因此，我们将 API 视为这三种类型的 Java 语言构造。为了唯一标识一个 Java API，我们遵循 Java 反射 [33] 的实践来检索类及其成员。具体来说，我们用 full_class_name（即全限定名）来表示一个类，它由类的包名和短名组成。

类中的字段用一对字符串表示：

```
⟨full_class_name, field_name⟩
```

方法可以用一个三元组字符串唯一标识：

```
⟨full_class_name, method_name, parameter_list⟩
```

其中最后一项是方法形式参数类型的（可能为空的）字符串列表。

使用这种表示法，构造函数可以表示为具有特殊名称 `<init>` 的方法 [2]。值得注意的是，我们的表示法充分包含了嵌套类及其成员。另请注意，回调是一种特殊方法，其控制权被反转到应用框架 [23]，因此我们的表示法可以在不需要额外适配的情况下覆盖它们。

### 2.3 JAR 列表

android.jar 文件是 Android SDK 的重要组成部分。它可以通过 SDK Manager 工具 [11] 下载，或通过 Android 源代码的 sdk target 构建。该文件包含在特定 API 级别定义 Android 应用框架的已编译 Java 类和资源的集合。通过链接此文件，开发者可以访问 Android 框架的类、字段和方法。这使他们能够编写利用平台特性（如电话或定位服务）的 Java 代码。值得注意的是，该文件不包含 API 方法的实际实现。它们的实际实现驻留在运行设备中。图1显示了 API 级别 33 的 android.jar 中的 `Service` 类，包含一个整型常量字段和两个方法桩。

```java
package android.app;

import android.content.ContextWrapper;

public class Service extends ContextWrapper {
    public static final int START_STICKY = 1;
    // other API fields...

    @Deprecated
    public final void stopForeground(boolean removeNotification) {
        throw new RuntimeException("Stub!");
    }

    public final void stopSelf() {
        throw new RuntimeException("Stub!");
    }
    // other API methods...
}
```

**图1：android.jar 文件中的反编译代码片段**

**2.3.1 API 提取。** 我们使用 Soot [27] 加载 android.jar 文件中的所有类。然后，对于每个成功加载的类，我们遍历其字段和方法列表以获取所有声明的 API。我们还提取了没有声明成员的类，例如 Serializable 接口。值得一提的是，我们不区分抽象类、接口、枚举类或注解声明。所有这些都可以被视为 Java 类的特殊形式，而它们的概念差异不影响我们的研究结果。

### 2.4 XML 列表

api-versions.xml 文件也捆绑在 Android SDK 中。它在构建 SDK 时与 android.jar 文件一起生成。通过引用此文件，可以确定一个 API 的最小和最大 API 级别。这些信息对于确保应用与所需 Android 版本范围兼容非常重要。Lint 利用此文件构建数据库，支持快速查找某个 API 在特定 API 级别的状态（如可用、废弃）。图2显示了此文件的片段，它显示了与图1相同的 API 信息。然而，它提供了更多关于 API 生命周期的信息，例如 API 何时被废弃。值得注意的是，此文件还包含被移除的 API，通过其 XML 元素上的 removed 属性来指示。这使 Lint 能够确定 API 的生命周期。

```xml
<class name="android/app/Service" since="1">
    <extends name="android/content/ContextWrapper"/>
    <method name="setForeground(Z)V" removed="11"/>
    <method name="stopForeground(Z)V" since="5" deprecated="33"/>
    <method name="stopSelf()V"/>
    <!-- other API methods... -->
    <field name="START_STICKY" since="5"/>
    <!-- other API fields... -->
</class>
```

**图2：api-versions.xml 文件中的一个类**

**2.4.1 API 提取。** 我们直接解析 api-versions.xml 文件来提取所有声明的 API。特别是，我们丢弃了具有 removed 属性的元素，因为我们关注的是特定 API 级别下可用的 API。

### 2.5 TXT 列表

TXT 列表指的是 Android 中的 current.txt 文件 [13]。一旦 API 发生变化并且触发 update-api 构建目标 [3]，它就会自动更新。PSDroid [54] 利用此文件构建 API 生命周期数据库，记录 API 何时被添加到 Android 框架以及何时被废弃。

TXT 列表与其他 AALs 的一个主要区别在于，该文件记录的是源代码级别的 API 签名。这种格式保留了在前端语言特性中会被擦除的字节码特征，例如泛型类型或可变参数（vararg）。源代码级别的签名有助于开发者更好地理解 API 的底层语义。然而，签名可能与 Android 字节码中引用的不同。

图3显示了 API 级别 33 的 current.txt 文件中的一个类条目示例。该文件使用一种特殊的上下文无关文法编写，其中每个类有多个部分：构造函数、方法、字段等。在图3中，方法 `getString` 有一个可变参数 `Object...`，它在编译时会被转换为 `Object[]`。后两个方法分别有类型参数 T 和无界通配符泛型类型参数。编译后，泛型类型被替换为 Object，类型参数被擦除。然后它们的方法声明变为：

```
String getString(int, Object[])
Object getSystemService(Class)
String getSystemServiceName(Class)
```

PSDroid 对其提取的 API 进行了此类转换，因此它们的数据库可以用于分析 Android 字节码中的 API 使用。

```
package android.content {
    public abstract class Context {
        // constructor
        ctor public Context();

        // API methods...
        method public final String getString(int,java.lang.Object...);
        method public final <T> T getSystemService(Class<T>);
        method public abstract String getSystemServiceName(Class<?>);

        // API fields...
        field public static final int MODE_WORLD_READABLE = 1; // 0x1
        field public static final String WINDOW_SERVICE = "window";
    }
}
```

**图3：current.txt 文件中的简化类条目**

**2.5.1 API 提取。** TXT 列表使用涉及许多源代码级语言特性的特殊文法编写。按照第2.2节中的 API 定义，我们实现了一个解析器来收集三组 API：类 C、字段 F 和方法 M。解析器还操作三个状态变量：当前包名 φ[t]、当前类名 θ[t] 以及泛型类型绑定的映射 Ω ⊂ {⟨GenericType ↦→ Type⟩*}。

解析器如图4所示。在规则1中，动作 φ[t{Id] 保存当前包名 Id。在规则2中，C ∪ {⟨φ[t].θ[t]⟩} 表示将当前包名和类名用点"."连接并将其添加到类集合中。类似地，规则3和4提取当前类中的成员字段和方法。规则5和6指定泛型类型的语义动作：为有界泛型类型创建映射 ⟨Param ↦→ Type⟩（规则5.1），或将无界泛型类型转换为 Object（规则5.2）。当遇到类型参数时，解析器将它们转换为其绑定的类型名称（规则6）。

**图4：TXT 列表文件的解析规则**
（规则1-6的数学表达，此处保留原文公式格式）

- 规则1（包定义）：`package Id { φ →t φ[t{Id]`
- 规则2（类定义）：`class Id[.Id]* [(extends|implements) Type] { θ →t θ[t{Id[.Id]*] C →t C ∪ {⟨φ[t].θ[t]⟩}`

### 2.6 CSV 列表

```
Landroid/content/Context;->MODE_WORLD_READABLE:I,public-api,sdk
Landroid/content/Context;->canStartActivityForResult()Z,max-target-r
```

**图5：hiddenapi-flags.csv 文件中的示例行**

从 Android 9 开始，一系列被称为非 SDK 接口（non-SDK interfaces）的 API 被限制在普通 Android 应用中使用 [6]。它们由 Android 系统内部使用，可能会在不通知的情况下发生变化。Android 提供了一个静态检查器 veridex [7] 用于扫描 Android 应用中的非 SDK 接口使用。它需要一个 CSV 文件 hiddenapi-flags.csv，其中列出了 API 及其阻止策略（如 public、条件阻止）。

图5显示了 CSV 文件的摘录。每行对应一个特定的方法或字段，即一个 API。与每个 API 关联的标签指定了其阻止策略。例如，第一行表示字段 `MODE_WORLD_READABLE` 是公开的。第二行表示 API 方法 `canStartActivityForResult()` 只能使用到 Android 11（代号 red velvet cake）。第三行表示 API `Context.destroy()` 不能在任何版本中被调用。需要注意的是，此文件只包含字节码级别的签名，这与图3中展示的 TXT 列表不同。

**2.6.1 API 提取。** 在 CSV 文件中，每行是方法或字段的 JNI 签名。我们从签名中提取它们的声明类来获取 CSV 列表中的 API 类。另请注意，在 Android 9（API 级别 28）中，非 SDK 接口被声明在多个非 CSV 文件中。我们简单合并所有文件以获得此 Android 版本的 CSV 列表。

CSV 列表与其他 AALs 的一个主要区别在于，前者包含构建 Android SDK 时编译的所有类。因此，CSV 列表涉及从高级 Java 语言特性合成的类或方法。例如，匿名类和 lambda 表达式是两种帮助开发者编写简洁源代码的前端 Java 表达式。在编译期间，它们会被合成为一些类或方法。这些合成 API 在 Java 字节码中被隐式调用，永远不会被 Android 应用使用。为了过滤掉这些 API，我们采用了一些启发式规则。例如，合成 API 通常遵循一些命名模式（如后缀 `Lambda\d+`），可以用来快速识别它们。我们还排除了合成的类初始化方法 [2]，它有一个特殊的方法名 `<clinit>`。平均而言，这些合成 API 占 CSV 列表中 API 的 8.7%。

## 3 实证研究

### 3.1 研究问题

本研究关注四种 AALs 的完整性和正确性。为了更深入地理解，我们还研究了真实 Android 设备上的 API 存在性和真实 Android 应用中的 API 使用情况。为了驱动我们的研究，我们提出以下研究问题（图6）：

- **RQ1（AAL 概览）**：四种 AALs 中有多少 API？它们在 Android 平台演化过程中如何变化？
- **RQ2（AAL 不一致性）**：四种 AALs 中包含的 API 之间有什么差异？

出于向后兼容性的考虑，Android API 移除是谨慎进行的 [32]。表3也支持这一点——新增的 API 通常多于移除的 API。然而，事实证明从 AALs 中移除的 API 仍然可能存在。以 TXT 中从 32 到 33 被移除的 569 个方法（表3最后一个单元格）为例。对于每个方法，我们在 Android 代码库中搜索 API 级别 32 和 33，并比较其在两个版本中的存在状态。其中，547（96.1%）个方法实际上已从代码库中移除。对于其余 22 个方法，其中 4 个被 @removed 注解标记并成为非 SDK 接口，另外 18 个在 API 级别 32 或 33 中均不存在。前者的一个例子是 `WebSettings.setAppCacheMaxSize(long)`，它在 32 中被标记为废弃，在 33 中其 Javadoc 字符串中后来被加上 @removed 注解。我们成功在运行 Android 13 的 Pixel 3 XL 设备上通过 Java 反射调用了此方法。这表明从 AALs 中移除的 API 仍然可以被应用访问，对基于 API 的兼容性问题检测器构成了健全性挑战。

> **发现2：** 从 AALs 中移除的 API 可能仍然存在于 Android 源代码或运行时中。

上述发现意味着 AALs 中声明的 API 与开发者实际可访问的 API 之间可能存在差异。为了更深入地了解这一情况，我们探索了四种 AALs 之间的差异（RQ2）并评估了它们在真实设备上的存在性（RQ3）。最后，我们评估了这些 AALs 在多大程度上覆盖了真实应用中的 API 使用（RQ4）。

### 3.5 RQ3：API 存在性

**3.5.1 方法。** 为了研究真实 Android 设备上的 API 存在性，我们开发了一个 Android 应用 AAL-Reflector。它接受相应运行时版本的 AALs，并尝试使用直接的 Java 反射 [33] 来访问它们的 API。这意味着 AAL-Reflector 只检索在类中显式定义的 API，而不从其父类搜索继承的 API。如果某个 AAL API 无法被反射，AAL-Reflector 将其视为不存在的 API。

AAL-Reflector 还统计非 AAL 字段和非 AAL 方法的数量。这里，"非 AAL 字段"指的是通过反射 API `Class.getDeclaredFields()` 列出但不存在于四种 AALs 中的字段。类似地，非 AAL 方法也被统计。为了查找非 AAL API，我们只使用四种 AALs 中的类，不搜索"非 AAL 类"。这是因为 Java 类加载是一个按需过程，在没有先验知识（Java 包名等）或对系统镜像的访问权限（需要 root 设备）[1] 的情况下，无法枚举所有可加载的类。

**3.5.2 设备池。** 我们在多台 Android 设备上运行 AAL-Reflector。具体来说，我们有六台具有定制操作系统的物理设备，涵盖三个 Android 版本。对于每个可用的 Android 版本，我们还创建了运行相应原版 Android 镜像的虚拟设备。总共使用了九台 Android 设备来研究 RQ3。

> **发现8：** 定制的 Android 设备广泛地在 Android 框架类中定义自己的 Java API。它们大多数具有公共访问级别。

### 3.6 RQ4：API 使用

**3.6.1 方法。** 我们实现了一个工具 APK-Analyzer 来分析应用（即 APK 文件）中的 API 使用。该工具集成了 Soot [27] 和 veridex [7]，并执行过程内流不敏感分析。具体来说，它扫描方法体以收集应用类中的三种类型 API 调用点：

1. **直接 API 调用：** 通过 FieldRef 或 InvokeExpr Jimple 表达式引用 API；
2. **额外 API 调用：** 使用 Android 包下但不存在于四种 AALs 中的 API；
3. **反射 API 调用：** 通过 Java 反射调用 API。这里我们直接解析 veridex 的输出并过滤出我们需要的 API 使用。

类型（2）和（3）的分析允许我们恢复超出 AALs 列表之外的被使用 API。另请注意，由于 JDK 类（如泛型集合）可以包含在 AALs 中，APK-Analyzer 会将它们从输出中丢弃，因为它们不在我们的研究范围内。

**3.6.2 应用数据集。** 我们从三个数据源收集了 APK 文件，每个数据源代表一种典型类型的 Android 应用：

- **开源应用：** F-Droid 是一个开源应用目录。它已被广泛用于 Android 相关研究 [48]。我们从 F-Droid 下载了所有 4,090 个可用应用。
- **商业应用：** Google Play 包含数百万个商业 Android 应用 [18]。为确保代表性，我们只收集了 AppBrain² 索引的 32 个类别中排名前 500 的应用。最终下载了 15,334 个 Google Play 应用。

  ² https://www.appbrain.com/apps/popular

- **Android 恶意软件：** 恶意软件可能表现出与正常应用不同的 API 使用 [47]。这里我们直接使用了 Cao 等人 [18] 收集的 1,238 个恶意应用样本。

对于收集的应用，我们丢弃了那些未调用 Android API或无法被 AAL-Analyzer 分析的应用（如混淆的 APK [41]）。排除后，剩余 4,046 个开源应用、12,968 个商业应用和 745 个恶意应用。总共 17,759 个真实 Android 应用构成了我们的实验数据集。

**3.6.3 结果。** 表6展示了按三种 API 调用类型分类的总体 API 使用情况。例如，在 4,046 个 F-Droid 应用中，全部都直接调用了四种 AALs 中的 API，总共使用了 24,973 个 API（字段和方法）。只有 1,601 个使用反射调用了总共 487 个 API 等。

所有应用都涉及直接 API 调用，这意味着每个应用至少调用一个 AAL 包含的 API（字段或方法）。此外，我们发现大多数直接调用的 API 是被四种 AALs 共享的那些。以 F-Droid 为例，使用了 24,973 个 AAL API（3,291 个字段和 21,682 个方法）。其中，1,738（52.8%）个字段和 15,825（73.0%）个方法出现在所有四种 AALs 中。同时，1,537（46.7%）个字段和 3,926（18.1%）个方法仅存在于 CSV 中。除此之外，F-Droid 应用还调用了 6 个 JAR 独有的方法和 27 个 XML 独有的方法。值得注意的是，JAR 中的内联成员（发现5）被真实应用所使用。从字节码访问内联成员是合法的，因为它们的访问可以在运行时动态分派。然而，如果静态分析器不涉及此类内联成员（即 CSV），这也为解析实际依赖的 AALs 中的 API 带来了挑战。Google Play 应用的结果与 F-Droid 类似。至于恶意软件，近 90% 的直接 API 调用是针对共享 API 的。

> **发现9：** 大多数 AAL API 使用针对四种 AALs 共享的公共 API。我们还观察到不可忽略的非共享 API 使用。

额外调用 API 的数量远多于 AALs 中的 API。这些 API 大多是 Android Support API（包 `android.support.*`）或 AndroidX API（包 `androidx.*`）[10]，它们被打包在 APK 文件中以确保向后 API 兼容性。它们可能被标识符重命名混淆 [19]，导致唯一 API 名称的爆炸。在 F-Droid 中，97.8% 的额外调用 API（包括被混淆的）是 Android Support API 或 AndroidX API。至于 Google Play 和恶意软件，百分比分别为 92.5% 和 89.8%。

有趣的是，我们观察到了厂商定制 API 的使用。具体来说，我们转储了额外调用 API 并检查它们是否与 RQ3 中在实验设备上发现的非 AAL API（表5）有交集。结果，我们在 F-Droid 应用中发现了 3 个非 AAL API 的调用点，在 Google Play 应用中发现了 78 个调用点。例如，一个开源应用 App Manager [14] 使用字段 `MIUI_OP_START` 来检查是否可以在 MIUI 系统上执行文件操作。

> **发现10：** 额外 API 调用主要是 Support 和 AndroidX API。来自 F-Droid 和 Google Play 的应用还包含厂商定制 API 的使用。

在我们收集的应用中，1,601（39.6%）个 F-Droid 应用包含反射调用。这一比例低于 Google Play 应用（89.5%）和恶意软件（48.3%）。通过与 CSV 文件比较，我们发现 F-Droid 中只有 12 个反射调用 API 是公共的，而在 Google Play 应用和恶意软件中，数字分别为 35 和 11。这表明真实应用中的大多数反射 API 调用针对的是非 SDK 接口（即非公共 API）。

> **发现11：** 商业应用和恶意软件比开源应用更倾向于使用反射调用非 SDK 接口。

## 4 讨论

### 4.1 我们发现的启示

- **从 Web 文档或源代码中提取 API 知识可能很困难。** Web 文档是出了名的不可靠 [16, 28]。至于 Android 源代码，研究者通常关注 Java 文件，而 Android API 也可以从其他编程语言生成（发现4）。此外，还应考虑内联成员，因为它们存在于应用的字节码中（发现9）。提取此类 API 对模拟编译器构成了重大挑战。Android Support 和 AndroidX 库也应被考虑（发现10）。

- **AALs 是不完整的、不一致的，甚至是不稳定的。** 没有任何一个 AAL 可以完全覆盖其他三个（图7）。即使最大的 AAL——CSV，也缺少测试 API（发现5）。此外，API 包含策略可能随时间变化（发现1）。因此，依赖特定 AALs 的工具需要注意潜在的 API 不匹配。例如，四个方法在 Android 13 中被从 TXT 列表移除，但它们仍然可以从 Android 运行时访问（发现2）。值得注意的是，我们发现数据集中有 5,055（39%）个 Google Play 应用调用了这些方法。

- **AALs 中的 API 可能不完全反映真实的 Android API。** AAL API 与 Android 源代码或运行时中存在的 API 之间存在差异（发现2）。特别是，JAR、XML 和 TXT 列表包含内联成员（图8），这些成员不被 CSV 包含。这些内联 API 也不存在于 Android 运行时（发现7）。因此，对静态和动态问题检测器采用不同的 API 处理是必要的。

### 4.2 对未来研究的建议

- **在解析 Android 源代码时要具体明确。** Android 代码库由一千多个子模块组成，使用数十种编程语言开发。因此，解析整个代码库来提取 Android API 并非易事。为了可复现性目的，最好呈现关于此过程的更多细节。例如，考虑了哪些编程语言或 Android 系统子模块，或者进行了哪些预处理（泛型类型擦除、成员内联等）。

- **根据任务选择合适的 AALs。** 我们研究的四种 AALs 在 API 包含策略上各不相同。因此，鼓励研究者在其研究的背景下提供更清晰的关于 AAL 特定应用的解释。例如，如果只关注核心 Android 功能，可以选择 TXT 列表；如果需要 Android 测试 API，使用 XML；如果需要原生/IPC API 分析，则使用 CSV。

- **进一步研究非 SDK API 和/或定制 API。** 除了正常的 Android API 外，我们还观察到非 SDK 接口和厂商定制 API 的使用。它们可能带来安全漏洞 [20] 和兼容性问题 [30]，最终会对终端用户产生负面影响。为了增强 Android 系统的安全性和隐私性，应投入更多研究力量来理解这些 API。

### 4.3 效度威胁

- **Android 版本和设备覆盖有限。** 我们的研究涵盖了六个 Android 版本和九台物理设备，这可能限制了发现的可推广性。虽然这些版本跨越了多个主要 Android 发行版本，设备包括原版 Android 和厂商定制系统，但它们可能无法完全代表 Android 生态系统的多样性，特别是考虑到 Android 版本的快速演化和新型设备的持续推出。因此，某些 API 行为或厂商特定的定制可能未被我们的分析捕获。

- **系统专用 API 的可访问性受限。** 某些 API 只能被系统应用访问，不能被第三方应用调用，即使通过反射也不行。因此这些 API 被 AAL-Reflector 视为不存在，因为 AAL-Reflector 专注于普通应用可访问的 API。在我们的分析中，只识别了少量此类 API，主要在 CSV AALs 中。由于这些 API 不适用于第三方应用，也不在大多数 Android 应用分析的范围内，我们未进一步调查。然而，这一限制可能影响明确针对系统级或特权应用的研究。

- **API 使用提取中的潜在不准确。** APK-Analyzer 实现的 API 使用提取过程可能存在构效威胁，它可能无法完美捕获应用中的所有 API 调用。为降低此威胁，我们将分析限制在应用级类，并依赖保守的提取规则。虽然这种方法提高了精度，但可能低估了某些应用中的总体 API 使用。未来工作可以纳入更高级的静态或混合分析技术来进一步提高提取准确性。

## 5 相关工作

### 5.1 关于 Android API 的实证研究

Android 开源项目（AOSP）是一个庞大而复杂的开源项目 [38]。因此，许多研究者致力于从 Android 代码库中挖掘实证知识。其中最早的工作由 McDonnell 等人 [42] 完成。他们研究了 17 个 Android 发行版本中的 SDK API 列表（即 XML 列表），并分析了 10 个开源应用对 API 变化的反应。他们表明，在 Android 4.2（API 级别 17）之后，Android API 经历了快速演化过程。他们还发现开发者倾向于避免频繁升级过时的 API。后来，Xia 等人 [53] 调查了开发者如何在 300,000 个应用的数据集上处理不兼容的演化 API。为了确定开发者是否为不兼容 API 提供替代实现，他们提出了一种基于 SVM 的方法 RAPID。他们发现开发者并不总是为不兼容 API 提供替代实现。同时，如果 Android 官方记录了 API 替换建议，开发者更愿意这样做。

研究者还研究了其他类别的 Android API。早在 2016 年，Li 等人 [30] 研究了 Android 框架中的不可访问 API，发现它们被广泛使用。这些不可访问 API 后来被宣布为非 SDK 接口的一部分，并由限制强制执行 [6]，构成了我们研究中 CSV 列表的受限 API。然而，Yang 等人 [55] 表明受限 API 仍然可以被普通应用访问。此外，Li 等人提出了 CDA [32]，从 Android 源代码中收集废弃 API。Liu 等人 [36] 研究了静默演化方法，这些方法会改变实现但保留原始文档。

### 5.2 Android 兼容性问题

Android 兼容性问题是一个长期存在的问题 [17]。最新的工具是 PSDroid [54]。它采用路径敏感的 API 调用分析和四种常见 API 使用检查模式，通过解析 TXT 列表文件来收集不兼容 API 列表。SAINTDroid [45] 是另一个近期工具，旨在检测三种类型的 API 兼容性问题。它直接解析 Android 源代码来获取 API 数据库。在它们之前，Liu 等人 [37] 对七个 Android 兼容性问题检测器进行了可复现性研究：ACID [39]、ACRYL [43, 44]、PIVOT [51]、CiD [31]、IctApiFinder [22]、FicFinder [50, 52] 和 CIDER [23]。他们的研究表明，具有系统化 API 收集方法的工具可以比没有该方法的方法获得更多的检测结果。这一发现突出了完整的不兼容 Android API 列表的重要性。我们的研究系统地分析了四种官方 AALs，这是对他们工作的补充。

兼容性问题可以动态暴露。JUnitTestGen [46] 能够生成兼容性问题触发的测试用例。它接受任意 API 列表并将 API 使用合成为单元测试用例。研究者还提出了自动修复此类 API 引起的兼容性问题的方法：RepairDroid [56] 使用领域特定语言来描述修复策略，AppEvolve [21] 从示例补丁中更新 API 使用。

除了 API 不兼容之外，Android 兼容性问题还可以表现在其他方面，如跨运行设备的 UI 不一致 [26]、配置项的不同处理方式 [24, 25]、系统权限机制的变化 [48] 等。

---

## 6 结论

本工作从关于 Android API 研究的系统性文献综述开始，从中总结了四种常用的官方 Android API 列表（AALs）。在对四种 AALs 的全面实证研究中，我们调查了 API 特征、差异、在真实设备上的存在性以及真实应用中的使用情况。基于我们的实证发现，我们为相关领域的未来工作得出了几点启示。我们的研究揭示了四种 AALs 之间的不稳定性和不一致性。它还指出了 Android 生态系统中非 SDK API 和厂商定制 API 的研究机会。我们的研究为从业者和研究者提供了宝贵的资源，帮助他们更深入地理解 Android API 和 API 列表。
