# Karpathy: Local Demo to Production, DevOps Is the Hardest Part
# Karpathy：本地 Demo 到线上产品，DevOps 是最难的部分

## 英文原文 / English Original

When I built menugen ~1 year ago, I observed that the hardest part by far was not the code itself, it was the plethora of services you have to assemble like IKEA furniture to make it real — the DevOps: services, payments, auth, database, security, domain names, etc.

I am really looking forward to the wave of abstraction and tooling to make this dramatically easier. E.g. Cursor or Windsurf already help a lot with the code itself, but the services remain.

Vibe coding menugen was an exhilarating and fun escapade as a local demo, but a bit of a painful slog as a deployed, real app.

---

## 中文翻译 / Chinese Translation

当我大约在一年前构建 menugen 时，我注意到**最难的部分绝对不是代码本身**，而是你需要像组装宜家家具一样拼装的大量第三方服务——也就是 DevOps：支付服务、用户认证、数据库、安全防护、域名配置等等。

我非常期待一波抽象和工具化的浪潮，让这件事变得简单得多。比如 Cursor 或 Windsurf 已经在代码层面提供了很大帮助，但那些服务仍然是个问题。

用 vibe coding 方式开发 menugen 作为本地 demo 是一场令人振奋的趣味冒险，但变成一个已部署的真实应用时，就变成了一场有点痛苦的持久战。

### 核心洞见

1. **Demo 和产品之间隔着一整个 DevOps 世界**：本地跑通 != 能上线运营
2. **AI 编程工具解决了一半问题**：代码写得出来，但第三方服务集成、安全合规、域名、支付等基础设施仍需大量人工
3. **vibe coding 的快乐止步于本地运行**：当需要配置 SSL 证书、调试支付网关、处理退款逻辑时，再酷的 AI 辅助也无济于事
4. **工具链抽象是下一个大机会**：市场需要能一站式搞定 auth、payments、database、deploy 的平台，而不是让每个开发者都重新造轮子

### 延伸观点

Karpathy 的观察揭示了 AI 应用开发的根本矛盾：

- **酷炫的 Demo vs. 枯燥的运维**：GenAI 应用的核心壁垒不在模型能力，而在工程化水平
- **AI 可以帮你写代码，但不能帮你签支付网关合同**：实体服务、法规合规、客服支持等物理世界的约束无法被 AI 绕过
- **平台机会**：Vercel、Supabase、Clerk 等公司正在解决这部分问题，但距离"一行命令搞定所有后端"还有距离

这提醒所有 AI 开发者：**Demo 融资金，Product 融盈利**，中间隔着的是你不愿面对但必须面对的 DevOps。
