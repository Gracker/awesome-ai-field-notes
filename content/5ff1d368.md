# The agent tax has arrived: Google Workspace's MCP pricing

> Source: https://martinalderson.com/posts/the-agent-tax-has-arrived/
> Author: Martin Alderson
> Published: 2026-11-27
> Fetched: 2026-11-28 from AK-RSS digest source note `2026-11-28-02-alderson-agent-tax.md`

## Digest source excerpt (grounding)

Google has [announced some major changes](https://workspaceupdates.googleblog.com/2026/11/mcp-servers-cli-standardized-usage-tiers-now-available.html) to their Google Workspace (Gmail, Google Docs and all related apps) pricing, as part of their new MCP rollout.

I think this is the first major product that's attempting to tax agentic use cases. I'm not sure it will work.

## What Google actually announced

Effectively two things. Firstly, all agents need to use MCP, not API to interact with Google. Quite how they plan on enforcing this I'm not sure, as the best I suspect they can do is behavioural profiling of what APIs get called, which seems to be quite difficult. I strongly believe this is mostly targeted at large AI companies and not smaller developers or solo users; but it is likely to have serious impact on any company that is (or will) start integrating agentic workflows into their products.

Secondly, a new pricing tier for said MCPs. In true Google style it's complicated, but in essence it's [a charge per 1000 requests](https://developers.google.com/workspace/guides/quota-cost-estimator), with different types of requests using different pricing tiers. Roughly speaking, you can read 1000 emails via MCP for $0.20.

There is a free tier of 5,000 calls a day, but this is grouped across all access for a specific Google Cloud project. Probably fine for solo use or a smaller business's internal agentic tooling, but past that it is going to be a major issue.

## The asymmetry: apps get a massive free allowance, agents don't

There is an enormous difference in the allowances for "legacy" applications using the REST API vs the new tiers for MCP.

On the REST API, each _user_ of the API gets its own allowance. On the free tier for REST, each user can do [6,000 quota units per minute](https://developers.google.com/workspace/gmail/api/reference/quota) of requests. This roughly equates to reading 100 emails a minute, _per user_. There is another project level cap of 20,000 emails a minute.

Previously going above this required a quota request but wasn't charged for. Now you have to move to the paid tier to go higher, but even there a REST app gets a huge free daily allowance - 10 million email reads a day - before it pays anything. MCP on the paid tier gets none.

So the real way to look at this is that if you are building a REST API you can read 20,000 emails a minute for free, but if you are building some agentic tooling you can read 5,000 emails a _day_ for free, and if you need more than that you get charged around $0.20 per thousand for every email you read, including the first 5,000.

It's an enormous difference, and puts the [Google Maps pricing changes](https://developers.googleblog.com/2018/05/introducing-google-maps-platform.html) of yore to shame in scale.

## Why is Google doing this?

I strongly suspect there are two key drivers.

Firstly, given Google has fumbled agentic workflows _so badly_ (until very recently, asking Gemini in Google Slides to bold some text would give you a "Sorry, can't do that" response), I'm sure that MCP access via OpenAI and Claude (and others) has absolutely exploded. The usage graph of these products with Google Workspace via MCP connectors must be going hyperbolic and no doubt has seriously ruffled the feathers of the product leadership at Google.

Given this, I suspect this is one way to throw some banana skins in the way of Anthropic and OpenAI. If you have business users paying $20/month for ChatGPT or Claude and many of these users read and search their Gmail from it, it starts becoming a _serious_ clip of their margins. If a user searches and reads emails adding up to 10,000 requests via the MCP, that is going to cost the frontier labs $2/month, _per user_. Given they do have significant compute costs against these subscription based users, it's likely to badly impact the unit economics of many of these accounts.

So I'm guessing the thoughts are at Google HQ they can stem the tide of users using MCP in _external_ products by making it expensive for those external AI products to use their Google Workspace data.

It also puts the frontier labs in a difficult position. They can either eat the cost of these MCP calls, which hurts margins at the worst possible time with investors combing through their financials as they become public companies. Or they can cap usage (and potentially pass the cost on), but this leads to a poor user experience, and perhaps shifts some people back to using Gemini for agentic tasks - as Gemini won't have these caps.

Secondly, I have had a feeling for a while that Google's search business is more fragile than it looks. Search revenue still grew 12% [last quarter](https://www.cnbc.com/2026/10/28/alphabet-googl-earnings-q3-2026.html), but that missed analyst estimates by over $1.5bn, and I think agents doing the searching instead of humans is only going to make that worse.

The revenue from this is small fry next to search. But it gives Google a story to tell investors: if agents are going to replace humans clicking around their products, they have a way to charge the agents instead.

## Who follows?

If this works out then I suspect we will see a rush of other companies trying the same strategy.

Any system of record - Salesforce, Atlassian, Intuit to name some at random - will be (very) tempted to try this strategy.

The difficulty is that you need to be _very_ sure that you really _are_ a system of record. Agents are eating a _lot_ of SaaS workflows. There is the risk this backfires entirely, and someone just downloads their data via CSV or some other old school mechanism and just has their agent query that.

Obviously at enterprise this is different. I still don't recommend anyone vibecode a Salesforce replacement, despite how many times I hear people thinking about it.
