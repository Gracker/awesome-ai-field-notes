# 夜天之书 #119：Agentic Coding 的边界

来源: https://mp.weixin.qq.com/s/x_FUUG4wBUqYs1H5DUtpgQ
作者: 夜天之书（tison）

## 核心论点

本文结合作者 Agentic Coding 的实践经验，深入讨论当前 LLM Coding Agent 的能力边界与局限性。文章指出：LLM 能够生成"疑似正确"的方案，但到"经得起考验的产品"之间存在 AI 无法覆盖的鸿沟。

## 主要观点

### 1. 软件工程即提示词

当前 LLM 的核心动作是对现有知识的搜索和组合，这推理出两个重要现象：

**现状代码多为浆糊（Big Ball of Mud）**：现实中程序员倾向于就地打补丁，导致 AI 训练的语料本身就充满问题代码。AI 容易生成"似是而非"的并发代码，因为能找到的并发代码语料本身就存在各种竞态条件。

**最佳实践依然有效**：利用现有软件工程实践（领域设计语言、限界上下文模块化、活文档）是提升 AI 生成代码质量的最佳路径。

### 2. 软工实践的反论

- **DRY 原则需谨慎**：过度抽象即"提前优化"，YAGNI 原则同样重要。AI 容易在错误的抽象层级上发散。
- **TDD 需有选择**：并非所有代码都需要高测试覆盖率，内部实现不需要追求 100% 覆盖。测试只能证明功能存在，不能证明 BUG 不存在。

### 3. 软件质量缺少可量化回归指标

AI Coding 的核心瓶颈在于：代码写得对不对、需求解决得好不好，除了可用测试验收的场景外，大部分现实需求无法建立可靠的回归指标。围棋有明确的"赢"作为目标，编程没有。这是 Agentic Coding 与 AI 围棋的本质区别。

### 4. 隐性知识需要真人提供

AI Coding 依赖大量上下文（项目规范、领域知识），这些隐性知识（业务判断、特殊场景解法）往往不在语料库中，需要真人持续提供。Review 带宽成为 Agentic Coding 的实际瓶颈。

### 5. 实用方法论

作者提出"人机协作"的实用模式：人负责核心设计和框架实现，AI 负责探索可能性和生成 stub，再由人定期维护。对于 Vibe Coding 的目标用户（需求简单、接受"差不多得了"），纯 AI 编程效果不错；但对于生产高质量软件，AI 提效上限明显。

## 结论

Agentic Coding 不会让软件行业发生根本性生产力革命，除非发现了能够验证代码质量的优秀工程回归指标。在此之前，AI Coding 的本质是辅助探索和生成，最终仍需人做全面 Review 和核心设计把控。
