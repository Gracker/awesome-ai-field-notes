## 核心发现

### 2. VSyncPredictor：基于 OLS 的 vsync 周期拟合

**源码位置**：`frameworks/native/services/surfaceflinger/Scheduler/VSyncPredictor.cpp`

**类签名（VSyncPredictor.h）**：

```cpp
class VSyncPredictor : public VSyncTracker {
public:
    VSyncPredictor(PhysicalDisplayId, nsecs_t idealPeriod, size_t historySize,
                   size_t minimumSamplesForPrediction, uint32_t outlierTolerancePercent);
    bool addVsyncTimestamp(nsecs_t timestamp) final;
    nsecs_t nextAnticipatedVSyncTimeFrom(nsecs_t timePoint) const final;
    nsecs_t currentPeriod() const final;
    void resetModel() final;
    void setPeriod(nsecs_t period) final;
    bool needsMoreSamples() const final;
    bool isVSyncInPhase(nsecs_t timePoint, Fps frameRate) const final;
    void setRenderRate(Fps) final;
    struct Model { nsecs_t slope; nsecs_t intercept; };
    VSyncPredictor::Model getVSyncPredictionModel() const;
    ...
};
```

**核心算法：`addVsyncTimestamp` 中的简单线性回归（OLS）**

源码中明确写出公式（注释完整保留）：

```
         Sigma_i( (X_i - mean(X)) * (Y_i - mean(Y) )
slope = -------------------------------------------
         Sigma_i ( X_i - mean(X) ) ^ 2

intercept = mean(Y) - slope * mean(X)
```

实现细节：

- `Y_i` = vsync 时间戳；`X_i` = 归一化到最旧时间戳后的 ordinal（缩放因子 `kScalingFactor = 1000` 用于定点运算）。
- 最小样本数：`kMinimumSamplesForPrediction`（构造时注入）。样本不足时直接返回 `{mIdealPeriod, 0}`，跳过拟合。
- 异常值过滤：百分比偏差 `|anticipatedPeriod - mIdealPeriod| / mIdealPeriod * 100 >= kOutlierTolerancePercent` 时清空时间戳环，重新学习。
- 样本数已满则使用环形缓冲 `mTimestamps[mLastTimestampIndex] = timestamp` 覆盖最旧样本。

**关键代码片段**（VSyncPredictor.cpp:140-220）：

```cpp
nsecs_t const anticipatedPeriod = top * kScalingFactor / bottom;
nsecs_t const intercept = meanTS - (anticipatedPeriod * meanOrdinal / kScalingFactor);

auto const percent = std::abs(anticipatedPeriod - mIdealPeriod) * kMaxPercent / mIdealPeriod;
if (percent >= kOutlierTolerancePercent) {
    it->second = {mIdealPeriod, 0};
    clearTimestamps();
    return false;
}
it->second = {anticipatedPeriod, intercept};
```

**`nextAnticipatedVSyncTimeFromLocked`（VSyncPredictor.cpp:240-265）—— 实际预测函数**

```cpp
nsecs_t VSyncPredictor::nextAnticipatedVSyncTimeFromLocked(nsecs_t timePoint) const {
    auto const [slope, intercept] = getVSyncPredictionModelLocked();
    if (mTimestamps.empty()) {
        auto const knownTimestamp = mKnownTimestamp ? *mKnownTimestamp : timePoint;
        auto const numPeriodsOut = ((timePoint - knownTimestamp) / mIdealPeriod) + 1;
        return knownTimestamp + numPeriodsOut * mIdealPeriod;
    }
    auto const oldest = *std::min_element(mTimestamps.begin(), mTimestamps.end());
    auto const zeroPoint = oldest + intercept;
    auto const ordinalRequest = (timePoint - zeroPoint + slope) / slope;
    auto const prediction = (ordinalRequest * slope) + intercept + oldest;
    LOG_ALWAYS_FATAL_IF(prediction < timePoint, "VSyncPredictor: model miscalculation");
    return prediction;
}
```

注意 `LOG_ALWAYS_FATAL_IF` 的兜底断言：模型预测出比当前时间更早的 vsync 即视为 bug。这通常发生在初学样本与理想周期偏差过大时。

**Render Rate Phase 补偿（VSyncPredictor.cpp:267-300）**

```cpp
nsecs_t VSyncPredictor::nextAnticipatedVSyncTimeFrom(nsecs_t timePoint) const {
    std::lock_guard lock(mMutex);
    mLastVsyncSequence = getVsyncSequenceLocked(timePoint);
    const auto renderRatePhase = [&]() -> int {
        if (!mRenderRate) return 0;
        const auto divisor = RefreshRateSelector::getFrameRateDivisor(
                Fps::fromPeriodNsecs(mIdealPeriod), *mRenderRate);
        if (divisor <= 1) return 0;
        const int mod = mLastVsyncSequence->seq % divisor;
        if (mod == 0) return 0;
        return divisor - mod;
    }();
    if (renderRatePhase == 0) return mLastVsyncSequence->vsyncTime;
    auto const [slope, intercept] = getVSyncPredictionModelLocked();
    const auto approximateNextVsync = mLastVsyncSequence->vsyncTime + slope * renderRatePhase;
    return nextAnticipatedVSyncTimeFromLocked(approximateNextVsync - slope / 2);
}
```

这是 Android 12 起 ARR（Adaptive Refresh Rate）的关键 —— 当应用通过 `setFrameRate()` 设定的渲染帧率不是显示刷新率的整数倍时，VSyncPredictor 把 vsync 序列对齐到应用请求帧率的最近相位，避免 jitter。

### 3. VSyncReactor：HW vsync 与 present fence 融合

**源码位置**：`frameworks/native/services/surfaceflinger/Scheduler/VSyncReactor.cpp`

**类层级**：`VSyncReactor` 继承 `VsyncController`，组合一个 `VSyncTracker&`（通常就是 `VSyncPredictor`）。这意味着 Reactor 只负责「采集样本并维护状态机」，真正的拟合交给 Tracker。

**两个时间源融合逻辑（addPresentFence + addHwVsyncTimestamp）**

Reactor 同时接受两种时间源：

1. **HW vsync 时间戳**（来自 HWComposer HAL 的硬件中断，`addHwVsyncTimestamp`）
2. **present fence**（surfaceflinger 提交 buffer 后由 HWC 回填，`addPresentFence`）

两者通过 `mTracker.addVsyncTimestamp(...)` 喂给同一个 Tracker。但 Reactor 维护自己的状态：

```cpp
mutable std::mutex mMutex;
bool mInternalIgnoreFences GUARDED_BY(mMutex) = false;
bool mExternalIgnoreFences GUARDED_BY(mMutex) = false;
std::vector<std::shared_ptr<android::FenceTime>> mUnfiredFences GUARDED_BY(mMutex);
bool mMoreSamplesNeeded GUARDED_BY(mMutex) = false;
bool mPeriodConfirmationInProgress GUARDED_BY(mMutex) = false;
std::optional<nsecs_t> mPeriodTransitioningTo GUARDED_BY(mMutex);
std::optional<nsecs_t> mLastHwVsync GUARDED_BY(mMutex);
hal::PowerMode mDisplayPowerMode GUARDED_BY(mMutex) = hal::PowerMode::ON;
const bool mSupportKernelIdleTimer = false;
```

**关键判定：`periodConfirmed`（VSyncReactor.cpp:145-180）—— 10% 容差**

```cpp
bool VSyncReactor::periodConfirmed(nsecs_t vsync_timestamp,
                                   std::optional<nsecs_t> HwcVsyncPeriod) {
    if (!mPeriodConfirmationInProgress) return false;
    if (mDisplayPowerMode == hal::PowerMode::DOZE ||
        mDisplayPowerMode == hal::PowerMode::DOZE_SUSPEND) {
        return true;
    }
    if (!mLastHwVsync && !HwcVsyncPeriod) return false;

    const bool periodIsChanging =
            mPeriodTransitioningTo && (*mPeriodTransitioningTo != mTracker.currentPeriod());
    if (mSupportKernelIdleTimer && !periodIsChanging) {
        HwcVsyncPeriod = {};
    }

    auto const period = mPeriodTransitioningTo ? *mPeriodTransitioningTo
                                              : mTracker.currentPeriod();
    static constexpr int allowancePercent = 10;
    static constexpr std::ratio<allowancePercent, 100> allowancePercentRatio;
    auto const allowance = period * allowancePercentRatio.num / allowancePercentRatio.den;

    if (HwcVsyncPeriod) {
        return std::abs(*HwcVsyncPeriod - period) < allowance;
    }
    auto const distance = vsync_timestamp - *mLastHwVsync;
    return std::abs(distance - period) < allowance;
}
```

**核心机制**：当 `mPeriodConfirmationInProgress=true` 时，新采集到的样本必须落在「期望周期 ±10%」范围内，才认为周期切换已稳定。这是 `startPeriodTransition()` → 等待若干帧确认 → `endPeriodTransition()` 状态机的判定核心。

**`startPeriodTransition`（VSyncReactor.cpp:125-140）**

```cpp
void VSyncReactor::startPeriodTransition(nsecs_t period, bool force) {
    ATRACE_INT64(ftl::Concat("VSR-", __func__, " ", mId.value).c_str(), period);
    std::lock_guard lock(mMutex);
    mLastHwVsync.reset();

    if (!mSupportKernelIdleTimer && period == mTracker.currentPeriod() && !force) {
        endPeriodTransition();
        setIgnorePresentFencesInternal(false);
        mMoreSamplesNeeded = false;
    } else {
        startPeriodTransitionInternal(period);
    }
}
```

注意 `force` 参数：当上层 ARR 强制要求重新校准时（即便周期未变），仍会进入 transition 流程。

### 4. VSyncDispatchTimerQueue：多客户端回调调度

**源码位置**：`frameworks/native/services/surfaceflinger/Scheduler/VSyncDispatchTimerQueue.cpp`

**核心数据结构**：`VSyncDispatchTimerQueueEntry` 持有

- `mName`：客户端标识
- `mCallback`：vsync 触发回调
- `mMinVsyncDistance`：最小回调间隔（避免抢占）
- `mArmedInfo`：{mActualWakeupTime, mActualVsyncTime, mActualReadyTime}
- `mScheduleTiming`：{earliestVsync, workDuration, readyDuration}

**核心算法：`schedule()`（VSyncDispatchTimerQueue.cpp:85-110）**

```cpp
ScheduleResult VSyncDispatchTimerQueueEntry::schedule(
        VSyncDispatch::ScheduleTiming timing, VSyncTracker& tracker, nsecs_t now) {
    auto nextVsyncTime = tracker.nextAnticipatedVSyncTimeFrom(
            std::max(timing.earliestVsync, now + timing.workDuration + timing.readyDuration));
    auto nextWakeupTime = nextVsyncTime - timing.workDuration - timing.readyDuration;

    bool const wouldSkipAVsyncTarget =
            mArmedInfo && (nextVsyncTime > (mArmedInfo->mActualVsyncTime + mMinVsyncDistance));
    bool const wouldSkipAWakeup =
            mArmedInfo && ((nextWakeupTime > (mArmedInfo->mActualWakeupTime + mMinVsyncDistance)));
    if (wouldSkipAVsyncTarget && wouldSkipAWakeup) {
        return getExpectedCallbackTime(nextVsyncTime, timing);
    }

    nextVsyncTime = adjustVsyncIfNeeded(tracker, nextVsyncTime);
    nextWakeupTime = nextVsyncTime - timing.workDuration - timing.readyDuration;
    auto const nextReadyTime = nextVsyncTime - timing.readyDuration;
    mScheduleTiming = timing;
    mArmedInfo = {nextWakeupTime, nextVsyncTime, nextReadyTime};
    return getExpectedCallbackTime(nextVsyncTime, timing);
}
```

**调用链总结**：

```
[App 或 HWC 请求]
  → Scheduler::requestNextVsync()
  → VsyncSchedule::getTracker().nextAnticipatedVSyncTimeFrom()
  → VSyncPredictor::nextAnticipatedVSyncTimeFromLocked()   [OLS 预测]
  → VSyncDispatchTimerQueueEntry::schedule()
  → 计算 wakeupTime = vsyncTime - workDuration - readyDuration
  → OneShotTimer 定时触发
  → VSyncDispatch::Callback  (例如 EventThread::onVSync)
```

### 6. Scheduler 与 Pacesetter Display

**源码位置**：`frameworks/native/services/surfaceflinger/Scheduler/Scheduler.cpp`

每个 display 注册时创建独立的 VsyncSchedule：

```cpp
void Scheduler::registerDisplay(PhysicalDisplayId displayId, RefreshRateSelectorPtr selectorPtr) {
    registerDisplayInternal(displayId, std::move(selectorPtr),
                            std::make_shared<VsyncSchedule>(displayId, mFeatures));
}
```

但调度时只使用 **pacesetter display**（主导显示器）的 vsync schedule：

```cpp
mSchedulerCallback.setPacesetterDisplay(...)
  → promotePacesetterDisplay(...)
  → applyNewVsyncSchedule(pacesetterVsyncSchedule)
```

Pacesetter 概念的意义：在多屏设备（折叠屏、外接显示器）上，所有 display 共享同一套 VSync 序列；否则 GPU 渲染提交顺序会变得不可预测。Android 14 起从「单一主显示」演化为「可切换 pacesetter」，主要由 `Scheduler::setPacesetterDisplay()` 触发。

## 性能影响

1. **预测模型收敛时间**：VSyncPredictor 默认 `kMinimumSamplesForPrediction` 由 Scheduler 创建时根据刷新率范围决定。120Hz 设备初次上电或显示模式切换后，约 6-10 个 vsync 周期（50-83ms @ 120Hz）即可输出稳定 slope。
2. **`mMinVsyncDistance` 设计**：避免单帧多次回调抢占造成 GPU pipeline bubble。游戏引擎和相机预览通常希望该值越小越好。
3. **`mPeriodConfirmationInProgress` 期间 cost**：在 ARR 切换刷新率时（如 60→90Hz），10% 容差 + 至少 2 帧确认（依赖 HWComposer 上报 hwcVsyncPeriod）导致短暂 ~17-33ms 的预测不可用窗口。这期间 SurfaceFlinger 退化为使用 `mIdealPeriod` 兜底。
4. **`kHistorySize` 滑动窗口**：默认 20（参考 Scheduler.cpp 构造参数）。环缓冲避免长 session 内存增长，同时保留足够样本做线性回归。
