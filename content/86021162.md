## 中文导读

论文以 SWE-bench 与 SWE-bench-Live 的 verified 子集为对象，用 Claude Opus 5、GPT 5.6、DeepSeek V4 Pro、Qwen 3.8 Max 搭配 SWE-agent 生成补丁，筛出 262 个存在多个正确解的实例，复用基准自带的 FAIL_TO_PASS 测试测量指令数与墙钟时间，并用 Welch ANOVA 替代此前工作的 RSD 做统计判别。结果显示：近半数实例的正确补丁之间存在显著性能差异；补丁运行性能与模型解题率几乎无关，模型排名近乎反转；部分补丁还存在正确性评测发现不了的架构级性能回退。作者据此主张仓库级修复能力的评测应把补丁性能纳入指标。

## 为什么值得关注

所有按 SWE-bench 解题率给模型排名的团队都值得对照这篇：在 pass 类指标之外，正确补丁的运行性能几乎是另一个正交的排名维度。方法上复用 FAIL_TO_PASS 测试做性能负载、以 Welch ANOVA 判别，成本低，评测管线可直接借鉴。

## English Abstract

Repository-level issue-resolution benchmarks such as SWE-bench evaluate submitted patches primarily based on whether they pass the correctness tests, leaving the runtime performance of different test-passing patches largely unexplored. Evaluating patch performance is essential but challenging since designing performance workloads for each benchmark instance is costly. However, these benchmarks already provide a natural candidate: the built-in FAIL_TO_PASS (F2P) tests, which exercise the behavior affected by the issue fix. We therefore investigate whether the provided F2P tests can be repurposed to evaluate patch performance. Overall, we choose four frontier models, Claude Opus 5, GPT 5.6, DeepSeek V4 Pro, and Qwen 3.8 Max, paired with SWE-agent to resolve the pre-filtered measurable corpus from verified splits of SWE-bench and SWE-bench-Live, yielding 262 cases with at least two different correct solutions, including the developer ground-truth patch. We then measure each solution's runtime performance in instruction count and wall-clock time on the native F2P test, and use Welch ANOVA instead of the RSD proposed in prior work as a more robust statistical discrimination criterion. We find that this methodology exhibits notable discrimination capability in runtime performance and identifies performance differences among patches in almost half of the instances. Our empirical study shows that the runtime performance of generated patches is independent of the issue resolution rate of LLMs, with nearly reversed model rankings. The case study also shows that the performance analysis reveals architectural regression in some patches that the correctness evaluation overlooked. These findings suggest that resolution rate does not adequately characterize LLMs' capability for repository-level issue resolution, motivating future evaluations to consider patch performance alongside it.
