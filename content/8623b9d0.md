## 核心发现

Jetpack Compose 状态管理的内存模型围绕三个核心组件：

1. **`MutableState<T>` / `MutableIntState` 等特化类型**（`SnapshotMutableStateImpl.kt` 与 `SnapshotIntState.kt`）：通用 `T` 版本必然装箱（`value: T` 是 `Any?`），原始类型特化版本（`mutableIntStateOf` 等）使用 `Int` 字段直接存储，彻底消除装箱。源码注释明确说明"values are stored in memory as the primitive `int` type, avoiding the autoboxing that occurs when using `MutableState<Int>`"。
2. **`RecomposeScopeImpl`**（`RecomposeScopeImpl.kt`）：每个 restartable composable 对应一个实例。其关键字段（`trackedInstances`、`trackedDependencies`）**采用 Lazy 分配**——仅当首次 `recordRead` 时才创建 `MutableObjectIntMap`/`MutableScatterMap`。一个不读任何 state 的纯静态 `@Composable` 函数连集合对象都不会分配。11 个 Boolean 状态用位标志打包到单个 `Int` 字段。
3. **`derivedStateOf` 的 `ResultRecord` 链**（`SnapshotState.kt` 与 `DerivedSnapshotState.kt`）：每次 `Snapshot.apply` 触发 snapshot 切换都会创建新 `StateRecord`，高频读写场景下每帧累计 N 个 record。Compose 1.12 修复了 Forward writes 导致的 composition 强引用泄漏（bug `b/516904513`）。

所有代码引用基于 `androidx-main`（Compose 1.8.x 系列，对应 Android 17 / API 37 的 AndroidX 库版本）。

## 源码分析

### 3.1 MutableState 的两类实现：装箱 vs 原生特化

源码位置：
- `compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/SnapshotState.kt`
- `compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/SnapshotIntState.kt`（IntState/LongState/FloatState/DoubleState 同目录）

**通用版本** `SnapshotMutableStateImpl<T>`（`SnapshotState.kt:136-148`）：

```kotlin
internal open class SnapshotMutableStateImpl<T>(
    value: T,
    override val policy: SnapshotMutationPolicy<T>,
) : StateObjectImpl(), SnapshotMutableState<T> {
    @Suppress("UNCHECKED_CAST")
    override var value: T
        get() = next.readable(this).value    // 读路径返回 T——Int 必然装箱
        set(value) =
            next.withCurrent(this) {
                if (!policy.equivalent(it.value, value)) {
                    next.overwritable(this, it) { this.value = value }
                }
            }

    private var next: StateStateRecord<T> =   // StateStateRecord.value 也是 T
        currentSnapshot().let { snapshot ->
            StateStateRecord(snapshot.snapshotId, value).also {
                if (snapshot !is GlobalSnapshot) {
                    it.next = StateStateRecord(Snapshot.PreexistingSnapshotId.toSnapshotId(), value)
                }
            }
        }
```

注意：通用 `T` 版本中 `value: T` 编译为 `Object` 字段。`StateStateRecord<T>(snapshotId, myValue)` 中的 `var value: T = myValue`（`SnapshotState.kt:202`）同样如此。**`mutableStateOf<Int>(0)` 的 value 字段在 JVM 上是 `Integer` 对象引用**，每次 `state.value` 读取会返回同一个 `Integer` 实例（由 JIT 缓存），但**写入路径上的 `value` 形参仍是装箱的**。

**原生特化版本** `SnapshotMutableIntStateImpl`（`SnapshotIntState.kt:143-198`）：

```kotlin
internal open class SnapshotMutableIntStateImpl(value: Int) :
    StateObjectImpl(), MutableIntState, SnapshotMutableState<Int> {

    private var next =
        currentSnapshot().let { snapshot ->
            IntStateStateRecord(snapshot.snapshotId, value).also {
                if (snapshot !is GlobalSnapshot) {
                    it.next =
                        IntStateStateRecord(Snapshot.PreexistingSnapshotId.toSnapshotId(), value)
                }
            }
        }

    override var intValue: Int
        get() = next.readable(this).value           // 直接返回 Int——零装箱
        set(value) =
            next.withCurrent(this) {
                if (it.value != value) {
                    next.overwritable(this, it) { this.value = value }
                }
            }

    // ...

    private class IntStateStateRecord(snapshotId: SnapshotId, var value: Int) :
        StateRecord(snapshotId) {
        override fun assign(value: StateRecord) {
            this.value = (value as IntStateStateRecord).value
        }
        // ...
    }
}
```

`IntStateStateRecord.value: Int` 是原始 `int` 字段（`SnapshotIntState.kt:188`），读取 `intValue` 直接返回原始类型。**`mutableIntStateOf` 在每帧读写的热路径上完全消除 `Integer` 装箱**。

源码注释（`SnapshotIntState.kt:38-49`）明确承诺这一行为：

> "The MutableIntState class is a single value holder whose reads and writes are observed by Compose. Additionally, writes to it are transacted as part of the Snapshot system. **On the JVM, values are stored in memory as the primitive `int` type, avoiding the autoboxing that occurs when using `MutableState<Int>`.**"

**工程意义**：在动画帧驱动的高频读写场景（如每帧 60 次的 progress 写入），从 `mutableStateOf(0)` 改为 `mutableIntStateOf(0)` 单变量可消除每帧 60 个 `Integer` 对象分配。在一个 100 项的 LazyColumn 中滚动，单帧可累计 6000 个 `Integer` 对象——这些都进入年轻代等待 minor GC。1.6 之前的 Compose 没有特化版本，这是 1.6+ 的重大内存改进（其他特化类型：`mutableLongStateOf`、`mutableFloatStateOf`、`mutableDoubleStateOf`）。

接口层 `IntState.value` getter 仍声明返回 `Int` 但有 `@Suppress("AutoBoxing")` 标记（`SnapshotIntState.kt:71`）——这是因为 `State<T>` 接口要求返回 `T`，但 Compose 编译器对调用方生成的代码会优先使用 `intValue` getter（无装箱）。

### 3.2 RecomposeScopeImpl 的 Lazy 字段分配策略

源码位置：`compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/RecomposeScopeImpl.kt`（449 行，2021 版权）。

**核心字段**（`RecomposeScopeImpl.kt:91-148`）：

```kotlin
internal class RecomposeScopeImpl(internal var owner: RecomposeScopeOwner?) :
    ScopeUpdateScope, RecomposeScope, IdentifiableRecomposeScope {

    /** The backing store for the boolean flags tracked by the recompose scope. */
    private var flags: Int = 0

    /** An anchor to the location in the slot table that start the group ... */
    var anchor: Anchor? = null

    /** The lambda to call to restart the scopes composition. */
    private var block: ((Composer, Int) -> Unit)? = null

    /** Tracks instances that were read in scope. */
    private var currentToken = 0
    private var trackedInstances: MutableObjectIntMap<Any>? = null    // ← Lazy 分配
    private var trackedDependencies: MutableScatterMap<DerivedState<*>, Any?>? = null  // ← Lazy 分配

    // ...
}
```

**关键观察**：`trackedInstances` 与 `trackedDependencies` 都是可空字段，且只在第一次需要时分配：

`trackedInstances` 在 `recordRead()` 中 Lazy 创建（`RecomposeScopeImpl.kt:301-309`）：

```kotlin
fun recordRead(instance: Any): Boolean {
    if (rereading) return false // Re-reading should force composition to update its tracking

    val trackedInstances =
        trackedInstances ?: MutableObjectIntMap<Any>().also { trackedInstances = it }

    val token = trackedInstances.put(instance, currentToken, default = -1)
    if (token == currentToken) {
        return true
    }
    return false
}
```

`trackedDependencies` 在 `recordDerivedStateValue()` 中 Lazy 创建（`RecomposeScopeImpl.kt:316-322`）：

```kotlin
fun recordDerivedStateValue(instance: DerivedState<*>, value: Any?) {
    val trackedDependencies =
        trackedDependencies
            ?: MutableScatterMap<DerivedState<*>, Any?>().also { trackedDependencies = it }

    trackedDependencies[instance] = value
}
```

**内存意义**：一个不含任何 state 读、不含 derivedState 的纯静态 `@Composable` 函数（仅做布局、调用其他子 composable），其 `RecomposeScopeImpl` 实例只占用：
- 对象头（Kotlin：12-16 字节）
- `owner: RecomposeScopeOwner?` 引用（4-8 字节）
- `anchor: Anchor?` 引用（4-8 字节）
- `flags: Int`（4 字节）
- `block: ((Composer, Int) -> Unit)?` 引用（4-8 字节）
- `currentToken: Int`（4 字节）
- 两个空引用字段（8-16 字节）

合计约 50-70 字节/实例。**只有真正读 state 的 composable 才付出 `MutableObjectIntMap` 与 `MutableScatterMap` 的代价**。

**11 个位标志**（`RecomposeScopeImpl.kt:73-83`）：

```kotlin
private const val UsedFlag = 0x001
private const val DefaultsInScopeFlag = 0x002
private const val DefaultsInvalidFlag = 0x004
private const val RequiresRecomposeFlag = 0x008
private const val SkippedFlag = 0x010
private const val RereadingFlag = 0x020
private const val ForcedRecomposeFlag = 0x040
private const val ForceReusing = 0x080
private const val Paused = 0x100
private const val Resuming = 0x200
private const val ResetReusing = 0x400
```

11 个 Boolean 打包到 1 个 `Int`，相比 11 个 Boolean 字段（Java boolean 在数组中 1 字节、独立字段 4 字节对齐），节省 ~30 字节/scope。这是 Jetpack Compose 在数十万 composable 的复杂页面上仍能保持可接受内存的关键设计。

**`release()` 路径**（`RecomposeScopeImpl.kt:218-224`）：

```kotlin
fun release() {
    owner?.recomposeScopeReleased(this)
    owner = null
    trackedInstances = null
    trackedDependencies = null
    block = null
}
```

离开 Composition 时（如 `if/when` 分支切换），`release()` 把所有引用置空——GC 可立即回收整个 scope 实例及其关联的 `MutableObjectIntMap`、`MutableScatterMap` 和 `block` Lambda。**这是 Compose 内存治理的核心契约**：开发侧写 `if (visible) ComposableA() else ComposableB()`，当分支变化时旧 scope 通过 `release()` 立即可回收，没有"延迟到页面销毁"的悬挂引用。

### 3.3 Scope 分配时机：插入 vs 重组 vs 重新激活

源码位置：`compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/GapComposer.kt`（3422 行）。

`GapComposer.addRecomposeScope()`（`GapComposer.kt:2119-2155`）控制何时创建新 `RecomposeScopeImpl`：

```kotlin
private fun addRecomposeScope() {
    if (inserting) {
        val scope = RecomposeScopeImpl(composition as CompositionImpl)
        invalidateStack.push(scope)
        updateValue(scope)
        enterRecomposeScope(scope)
    } else {
        val invalidation = invalidations.removeLocation(reader.parent)
        val slot = reader.next()
        val scope =
            if (slot == Composer.Empty) {
                // This code is executed when a previously deactivate region is becomes active
                // again. See Composer.deactivateToEndGroup()
                val newScope = RecomposeScopeImpl(composition as CompositionImpl)
                updateValue(newScope)
                newScope
            } else slot as RecomposeScopeImpl
        scope.requiresRecompose =
            invalidation != null ||
                scope.forcedRecompose.also { forced ->
                    if (forced) scope.forcedRecompose = false
                }
        invalidateStack.push(scope)
        enterRecomposeScope(scope)
        // ...
    }
}
```

**三个 scope 分配路径**：

| 路径 | 触发条件 | 新分配？ |
|------|----------|----------|
| `inserting == true`（首次组合） | 首次进入 Composition | 新分配 |
| `slot == Composer.Empty`（复活） | `if/when` 分支从隐藏变可见 | 新分配 |
| 否则（重组） | 重组路径 | **复用旧 scope**，仅设置 `requiresRecompose` 标记 |

**关键洞见**：重组不会分配新 `RecomposeScopeImpl`——这是 Compose 内存模型的核心稳定保障。**只有首次进入和分支切换才会分配新 scope**。`updateValue(scope)` 把 scope 实例存入 `SlotTable` 的 slot 数组（参见 §3.4）。

### 3.4 endRestartGroup 与 updateScope 的 Lambda 分配

源码位置：`GapComposer.kt:2158-2208`。

```kotlin
@ComposeCompilerApi
override fun endRestartGroup(): ScopeUpdateScope? {
    val scope = if (invalidateStack.isNotEmpty()) invalidateStack.pop() else null
    if (scope != null) {
        scope.requiresRecompose = false
        exitRecomposeScope(scope)?.let { changeListWriter.endCompositionScope(it, composition) }
        // ...
    }
    val result =
        if (scope != null && !scope.skipped && (scope.used || forceRecomposeScopes)) {
            if (scope.anchor == null) {
                scope.anchor =
                    if (inserting) {
                        writer.anchor(writer.parent)
                    } else {
                        reader.anchor(reader.parent)
                    }
            }
            scope.defaultsInvalid = false
            scope
        } else {
            null
        }
    end(isNode = false)
    return result
}
```

**`scope.used` 决定是否返回 `ScopeUpdateScope`**：当编译器生成的代码确实调用 `scope.updateScope { composer, _ -> ... }`（`RecomposeScopeImpl.kt:253-255`）时，`used = true`——意味着每次重组**确实会创建一个新的 Lambda 实例**替换 `block` 字段：

```kotlin
override fun updateScope(block: (Composer, Int) -> Unit) {
    this.block = block
}
```

旧的 Lambda 失去唯一引用后进入年轻代等待 minor GC。**这是章节中"每个 restartable composable 每次重组都分配一个新 Lambda"的源码级证据**。

调用链：`Snapshot 写入 → Recomposer.invalidate → invalidations.add → recompose → Composer.recompose → ComposerImpl.recordComposerModifications → ComposerImpl.performRecompose → ComposerImpl.recompose → addRecomposeScope → endRestartGroup → 编译器生成的 updateScope { ... } → scope.block = 新 Lambda`。

### 3.5 SlotTable 内部存储结构（与 2026-06-21 报告互为补充）

源码位置：`compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/composer/gapbuffer/SlotTable.kt`。

核心字段（`SlotTable.kt:131-180`）：

```kotlin
internal class SlotTable : SlotStorage(), CompositionData, Iterable<CompositionGroup> {
    var groups = IntArray(0)
        private set
    var groupsSize = 0
        private set
    var slots = Array<Any?>(0) { null }
        private set
    var slotsSize = 0
        private set
    private var readers = 0
    private val lock = makeSynchronizedObject()
    internal var writer = false
        private set
    internal var version = 0

    internal var sourceInformationMap: HashMap<GapAnchor, GapGroupSourceInformation>? = null

```

字段编码常量（`SlotTable.kt:3893-3937`）：

```kotlin
// Group layout
//  0             | 1             | 2             | 3             | 4             |
//  Key           | Group info    | Parent anchor | Size          | Data anchor   |
private const val Key_Offset = 0
private const val GroupInfo_Offset = 1
private const val ParentAnchor_Offset = 2
private const val Size_Offset = 3
private const val DataAnchor_Offset = 4
private const val Group_Fields_Size = 5

// The minimum number of groups to allocate the group table
private const val MinGroupGrowthSize = 32

// The minimum number of data slots to allocate in the data slot table
private const val MinSlotsGrowthSize = 32
```

**`Group_Fields_Size = 5` 验证了章节中的"组信息每组占 5 个 int"**。`GroupInfo` 字段是位打包：
- bit 31：Node（是否为节点组）
- bit 30：ObjectKey（是否含 ObjectKey）
- bit 29：Aux（是否含 Aux）
- bit 28：Mark
- bit 27：ContainsMark
- bit 0-25：NodeCount（26 位，最大 ~6700 万）

`MinGroupGrowthSize = 32` 意味着 SlotTable 首次扩容直接到 32 组（160 个 int = 640 字节），避免了小页面的多次扩容抖动。这与 2026-06-21 报告中描述的 2× 倍增策略结合，最坏情况是 32 → 64 → 128 → ... 的几何扩张。

`RecomposeScopeImpl` 实例作为对象引用存储在 `slots: Array<Any?>` 中（参见 `GapComposer.addRecomposeScope` 中的 `updateValue(scope)`）——每次新 scope 分配会消耗一个 slot。

### 3.6 derivedStateOf 的内存语义与 Compose 1.12 修复

源码位置：`compose/runtime/runtime/src/commonMain/kotlin/androidx/compose/runtime/SnapshotState.kt`（中段 `DerivedSnapshotState` 类）；以及 Compose 1.12 的公告（`androidx-main` 分支 changelog：`Ib5d87, b/516904513`）。

**`derivedStateOf { ... }` 创建的 `DerivedSnapshotState` 实例**继承自 `SnapshotMutableStateImpl`：

- 每次 `Snapshot.apply` 触发 snapshot 切换（其他 State 写入），`derivedStateOf` 的 `ResultRecord` 链追加新记录；
- `ResultRecord.dependencies: ObjectIntMap<StateObject>` 在每次 `calculation` 块执行后更新；
- 列表项内 `derivedStateOf` 在快速滚动时每帧 N 个 record，**直到下次 minor GC**。

**Compose 1.12 修复（`b/516904513`）**：

> "Fixed an issue where forwarding writes to objects read by a derived state caused the `derivedStateOf()` instance to be retained by the composition until the composition is disposed."

**根因**：`derivedStateOf` 实例通过 `trackedDependencies` 被 `RecomposeScopeImpl` 强引用，scope 又被 SlotTable 强引用。当 `derivedStateOf` 内部读取的对象（如 ViewModel 中的 StateFlow）发生 Forward write（先写入 derived 再写入底层），会形成引用链：`composition → SlotTable → RecomposeScopeImpl → trackedDependencies → DerivedSnapshotState → 外部对象`。**LazyColumn 快速滚动时，scope 反复销毁/重建，但 derivedState 实例仍被旧的、已不在使用中的 scope 引用**——直到 composition 整体 dispose 才回收。

修复路径：让 `DerivedSnapshotState` 不再通过 `trackedDependencies` 形成强引用闭环，或在 scope `release()` 时显式断开引用。

**工程实践**：
- 列表项内避免 `derivedStateOf`——直接 `remember(list, index) { ... }`；
- 若必须用，确保 `derivedStateOf` 块的依赖项是稳定的（不引用 ViewModel 的可变 StateFlow）；
- 在 Android 17 / Compose 1.8.x 之前（API 37）的版本上要警惕这个泄漏。

## 版本差异

| 特性 | Compose 版本 | Android 版本 | 影响 |
|------|------------|------------|------|
| `mutableIntStateOf` 等原生特化 | 1.6+ (2023-07) | Android 14+ | 消除 Int/Long/Float/Double 装箱 |
| Strong Skipping Mode（注解生成器） | 1.5.4+ 稳定 | Android 13+ | 自动跳过不可比较参数的 composable |
| Pausable Composition | 1.7+ (2024-09) | Android 16+ | 复杂页面的 lazy layout cache window |
| `derivedStateOf` Forward write 修复 | 1.12.0-beta01+ | Android 18 / API 38 | **超出 AIW 范围，仅作记录，不写入 Android 17 结论** |

注：原生特化 State 在 Compose 1.6 之前不存在，1.6 之前所有 `mutableStateOf<Int>` 都装箱。Compose 1.6+ 提供的特化版本（`mutableIntStateOf`、`mutableLongStateOf`、`mutableFloatStateOf`、`mutableDoubleStateOf`）在 API 上完全兼容，IDE 会给出 lint 提示。

## 性能影响

**单变量优化前后对比**（基于源码静态分析与 Compose 官方基准模式估算）：

- `mutableStateOf<Int>(0)` + 每帧读写 1 次 → 每帧分配 1 个 `Integer`（或 0 个，依赖 JIT 缓存）
- `mutableIntStateOf(0)` + 每帧读写 1 次 → 每帧 0 个分配
- LazyColumn 100 项滚动 → `mutableStateOf` 版本单帧 100 个 `Integer`；`mutableIntStateOf` 版本 0 个

**`RecomposeScopeImpl` 实例数估算**：

- 中等页面（50 个 restartable composable）首次组合：50 个 scope × ~50 字节 = ~2.5 KB
- 每个 scope 的 `trackedInstances` 平均 5 个 state 引用 + 5 个 int token × 8 字节/项 = ~80 字节
- 每个 scope 的 `block` Lambda 对象（首次组合时）= ~80-120 字节（含 captured state）
- 50 个 scope 全功能激活后静态占用 ≈ 2.5 + 4 + 5 ≈ 11 KB（不含 SlotTable 本身）

**结合 SlotTable 的内存**（参 2026-06-21 报告）：

- 50 个 composable 的 groups 数组容量（50 组 × 5 int = 1000 字节，倍增到 32 的整数倍后实际 160 组 × 5 × 4 = 3200 字节）
- 50 个 scope 的 slots 数组（Array<Any?>，8 字节/引用 + 对象头）= ~400 字节
- SlotTable 总占用约 4 KB

总静态内存约 15 KB/页面。**这个数字在 Android 17 / API 37 设备（普遍 8GB+ RAM）上是可接受的**，但在低端机（API 29 / Android 10 入门级 1-2GB 设备）上是页面切换卡顿的潜在因素。
