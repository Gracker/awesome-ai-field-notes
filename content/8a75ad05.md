## 中文导读

LLM agent 的工具调用字节会在协议栈里被多次解析：provider、网关、SDK、框架、guard、executor 各解析一次，而 JSON 把重复 key 以哪份为准这类决定留给解析器。一旦 guard 和 executor 解析结果不同，guard 批准一个调用、executor 执行另一个，审计日志里只有被批准的那个——论文称之为 tool-call smuggling。作者归纳出 6 种同字节异解析方式，构建差分测试 harness，对 17 个固定的解析/校验配置喂同一字节：多数两两组合在某些输入上分歧，两个官方 MCP SDK 也接受不同输入。在 τ-bench 和 AgentDojo 任务上，能改写传输字节的攻击者可取消他人预订、创建被 guard 按名字封锁的文件，日志却只记录批准调用。防御：整条调用只解析一次（含 JSON 文本）、只保留批准 schema 的字段、用 call ID 封签传输，挡下全部 7,412 个构造输入。

## 为什么值得关注

这是对 agent 安全边界的协议层拆解：薄弱点不在模型是否被注入，而在同一字节被解析多次、各解析器默认彼此一致这个假设上。对做 MCP/工具网关和 agent 审计日志的团队，这是一份必须对齐的实现细节清单。

## 关键信息

- 标题：Oops!... I Parsed It Again: Tool-Call Smuggling Against LLM Agents
- arXiv：2611.30624，2026-11-23，cs.CR / cs.AI / cs.SE
- 问题：工具调用的同一字节被 provider/网关/SDK/guard/executor 多次解析，JSON 重复 key 等解析分歧可让 guard 批准的调用与 executor 实际执行的调用不一致，审计日志失真
- 方法：归纳 6 种同字节异解析方式；差分测试 17 个固定解析/校验配置；在 τ-bench、AgentDojo 上构造真实攻击（取消他人预订、创建被封锁文件、借恶意 schema 多余字段外传用户数据）；测 10 个模型在调用与参数文本中写入重复/伪装 key 的行为
- 结果：多数解析器两两分歧，两个官方 MCP SDK 亦然；被测模型不在调用本身写重复 key，但会原样把 key 复制进参数 JSON 文本，被 Python guard 与 Go executor 不同解读

## English Summary

Tool-call smuggling exploits that the same tool-call bytes are parsed repeatedly across the stack (provider, gateways, SDKs, frameworks, guard, executor) while JSON leaves parser-dependent choices such as which repeated key counts. When guard and executor parse differently, the approved call and the executed call diverge and the audit log records only the approved one. The paper describes six ways identical bytes yield different calls and differential-tests 17 pinned parser/validator configurations: most pairs disagree on some inputs, including two official MCP SDKs. On τ-bench and AgentDojo tasks, an attacker rewriting bytes in transit cancels another customer's reservation and creates a file the guard blocks by name, with only the approved call logged. A mitigation that parses each call once (JSON text included), keeps only approved-schema fields, and seals it with its call ID in transit stops all 7,412 crafted inputs and every attack built.
