## 核心发现

Android 17 的 Binder 用户态链路（libbinder + 内核 `drivers/android/binder.c`）由 **5 个互相耦合的调优杠杆**构成：

1. **1 MB mmap 事务缓冲区**（`BINDER_VM_SIZE = 1MiB - 2×PAGE_SIZE`，`ProcessState.cpp:48`）——这是单进程所有 async/sync 事务共享的环形物理页池，超出后驱动返回 `-ENOSPC` 并把上层映射为 `FAILED_TRANSACTION`
2. **默认 15 个 binder 线程**（`DEFAULT_MAX_BINDER_THREADS=15`，`ProcessState.cpp:49`）——`setThreadPoolMaxThreadCount()` 可上调但不可下调（`LOG_ALWAYS_FATAL_IF`）
3. **`BINDER_WRITE_READ` 单次 ioctl 双向传输**——`IPCThreadState::talkWithDriver()` 始终合并 write/read 请求；`flushCommands()` 必须调用两次才能稳定清空 post-write deref 命令
4. **oneway vs sync 的「一次额外 wait」差**——sync 调用 `waitForResponse(reply)` 一直阻塞到 `BR_REPLY`；oneway 调用 `waitForResponse(nullptr, nullptr)` 仅等到 `BR_TRANSACTION_COMPLETE` 即可返回
5. **oneway spam detection + frozen reply 双重软限流**——`BR_ONEWAY_SPAM_SUSPECT` 是诊断信号；`BR_FROZEN_REPLY` 在 Android 12+ 把进程冷冻期的 oneway 调用立即反馈成 `FROZEN_OBJECT`

## 源码分析

### 1. mmap 事务缓冲区：`BINDER_VM_SIZE`

**位置**：`frameworks/native/libs/binder/ProcessState.cpp:48`（同时被 `kernel/common/drivers/android/binder_alloc.c` 验证）

```cpp
// ProcessState.cpp:48-49
#define BINDER_VM_SIZE ((1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2)
#define DEFAULT_MAX_BINDER_THREADS 15
```

`ProcessState` 构造时执行 `mmap(nullptr, BINDER_VM_SIZE, PROT_READ, MAP_PRIVATE | MAP_NORESERVE, opened.get(), 0)`（`ProcessState.cpp:625`）。这块虚拟地址空间由**内核 binder_alloc** 懒分配物理页（`binder_mmap` → `binder_alloc_mmap_handler`，`drivers/android/binder.c:6219`）。

**调优含义**：

- 单进程所有 in-flight 事务（sync + oneway + reply）共用这块环形页池。Android 默认的 1 MB 减去 2 个 page（典型的 16 KB）后约 **1008 KB**
- 高频 oneway 场景下，接收端未及时消费会占满 buffer，触发 `binder_alloc_new_buf()` 返回 `-ENOSPC` → Java 层表现为 `FAILED_TRANSACTION`
- **这是 Android 12+ 引入 binder freezer 后 oneway 调用的"软瓶颈"**：frozen 进程无法消费 async 事务，buffer 累积到上限时上游会被反馈 `BR_TRANSACTION_PENDING_FROZEN` 而不是 `BR_FROZEN_REPLY`（详见 §5）

> [已验证：AOSP android-17.0.0_r1 frameworks/native/libs/binder/ProcessState.cpp 第 48-49、625 行；kernel/common drivers/android/binder.c binder_mmap 在 android-mainline 6.12 中位于 6219]

### 2. 线程池：`DEFAULT_MAX_BINDER_THREADS=15` 与不可下调

**位置**：`ProcessState.cpp:49`、`:451-460`、`:611`

```cpp
status_t ProcessState::setThreadPoolMaxThreadCount(size_t maxThreads) {
    LOG_ALWAYS_FATAL_IF(mThreadPoolStarted && maxThreads < mMaxThreads,
           "Binder threadpool cannot be shrunk after starting");
    ...
    if (ioctl(mDriverFD, BINDER_SET_MAX_THREADS, &maxThreads) != -1) {
        mMaxThreads = maxThreads;
    }
}
```

**调用方使用模式**：

| 阶段 | 推荐做法 | 关键调用 |
|------|---------|---------|
| 启动前 | 配置 `maxThreads` | `setThreadPoolMaxThreadCount(N)` |
| 主线程 | 启动主线程 | `startThreadPool()`（+1 线程） |
| 服务注册 | 维持线程池 | `joinThreadPool()`（再 +1） |

**调优含义**：

- 总线程数 = `1 (startThreadPool) + maxThreads (kernel 启动) + N (joinThreadPool)`
- 默认 15 线程在 system_server / systemui 足够，但 **surfaceflinger / 第三方常驻服务**通常需要在 manifest 阶段把 `maxThreads` 调到 31~63
- 内核在 `BINDER_SET_MAX_THREADS` 后会**按需**唤醒线程：每次 `binder_transaction` 发现 thread todo 空且 target process 未达 max，会自动 `binder_wakeup_thread_ilocked(proc, NULL, !oneway)`（`binder.c:3075`）

### 3. 单次 ioctl 双向传输：`talkWithDriver` 与 flushCommands 双调用

**位置**：`IPCThreadState.cpp:1246-1363`

```cpp
status_t IPCThreadState::talkWithDriver(bool doReceive)
{
    ...
    binder_write_read bwr;
    bwr.write_size = outAvail;
    bwr.write_buffer = (uintptr_t)mOut.data();
    if (doReceive && needRead) {
        bwr.read_size = mIn.dataCapacity();
        bwr.read_buffer = (uintptr_t)mIn.data();
    } else {
        bwr.read_size = 0;
        bwr.read_buffer = 0;
    }
    ...
#if defined(BINDER_WITH_KERNEL_IPC)
    if (ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr) >= 0)
        err = NO_ERROR;
    else
        err = -errno;
#endif
}
```

**关键观察**：

- **单次 ioctl 同时发命令 + 收 BR_***——这是 Android Binder 与传统 socket 最大的性能差异之一
- `doReceive=false` 时（如 `flushCommands`、`joinThreadPool` 启动时），`bwr.read_size=0`，纯发送
- `flushCommands()`（`IPCThreadState.cpp:664-688`）**故意调用两次** `talkWithDriver(false)`：第一次发送 BC_* 命令并让内核处理 incStrong 的临时引用，第二次处理 post-write deref（`incStrongHandle/incWeakHandle` 留下的 `mPostWriteStrongDerefs`/`mPostWriteWeakDerefs`）

```cpp
status_t IPCThreadState::flushCommands() {
    if (status_t res = talkWithDriver(false); res != OK) { ... }
    if (status_t res = talkWithDriver(false); res != OK) { ... }  // 收敛 post-write deref
    ...
}
```

**调优含义**：

- 单次 `transact` 的最小开销 = 2 次 ioctl（同步路径）/ 1 次 ioctl（oneway 路径）
- `flushCommands()` 的「双调用」是 Android 17 相比 Android 10 重要的稳定性改进，确保 BC_INCREFS 临时引用在 BC_TRANSACTION 提交后立即被服务端处理

> [已验证：AOSP android-17.0.0_r1 frameworks/native/libs/binder/IPCThreadState.cpp 第 664-688 行 flushCommands、第 1246-1363 行 talkWithDriver]

### 4. 同步 vs oneway 的 waitForResponse 差异

**位置**：`IPCThreadState.cpp:921-998`（`transact`）、`:1143-1244`（`waitForResponse`）

**sync 路径**（flags & TF_ONE_WAY == 0）：

```cpp
if ((flags & TF_ONE_WAY) == 0) {
    ...
    if (reply) {
        err = waitForResponse(reply);
    } else {
        Parcel fakeReply;
        err = waitForResponse(&fakeReply);
    }
}
```

**oneway 路径**：

```cpp
else {
    err = waitForResponse(nullptr, nullptr);  // 仅等 BR_TRANSACTION_COMPLETE
}
```

`waitForResponse` 内 switch 循环里：

```cpp
case BR_TRANSACTION_COMPLETE:
    if (!reply && !acquireResult) goto finish;  // oneway 命中此分支立即返回
    break;
case BR_REPLY:
    ...
    goto finish;  // sync 命中此分支
```

**调优含义**：

- sync 调用最少 2 次 ioctl（write transaction + wait reply），oneway 至少 1 次 ioctl
- **当 callee 端 binder 线程被占满时**，sync 调用方会被阻塞在 `talkWithDriver` 内；oneway 调用方则可以立即返回——这是 oneway 的核心性能优势
- 但是：oneway 仍需 `BC_FREE_BUFFER` 命令回收内核缓冲区，这一步会在下一次 sync 调用或 `flushCommands` 时合并提交（避免额外 ioctl）

### 5. oneway spam 检测与 frozen reply：软限流机制

**位置**：
- `ProcessState.cpp:538-563`（`isDriverFeatureEnabled` + `enableOnewaySpamDetection`）
- `IPCThreadState.cpp:1206-1213`（`BR_ONEWAY_SPAM_SUSPECT` / `BR_FROZEN_REPLY` 分支）

```cpp
case BR_ONEWAY_SPAM_SUSPECT:
    ALOGE("Process seems to be sending too many oneway calls.");
    CallStack::logStack("oneway spamming", CallStack::getCurrent().get(),
            ANDROID_LOG_ERROR);
    [[fallthrough]];
case BR_TRANSACTION_COMPLETE:
    if (!reply && !acquireResult) goto finish;
    break;

case BR_FROZEN_REPLY:
    err = enableFrozenObjectErrorCode() ? FROZEN_OBJECT : FAILED_TRANSACTION;
    goto finish;
```

**调优含义**：

- `BR_ONEWAY_SPAM_SUSPECT` 由内核在同一个进程占用过多 async buffer 时通过 `oneway_spam_suspect` 标志触发，**仅是诊断信号，不限流**（驱动会发送 `BINDER_ENABLE_ONEWAY_SPAM_DETECTION` ioctl 启用该检测）
- `BR_FROZEN_REPLY` 在进程进入 freezer 后被 oneway 调用立即触发，`enableFrozenObjectErrorCode()` 由 `android::os::binder::flags::enable_frozen_object_error()` 控制（系统属性可调）
- 这两条是 Android 17 IPC 调优的**主要监控指标**，Perfetto 抓 binder 段时若看到大量 `BR_ONEWAY_SPAM_SUSPECT` 或 `BR_FROZEN_REPLY` 是服务异常信号

## 调优杠杆总结

| 杠杆 | 默认值 | 源码位置 | 调优方向 |
|------|--------|---------|---------|
| mmap 缓冲区 | 1 MiB - 2 page | `ProcessState.cpp:48` | 不可调（编译时常量），靠消费速度调节 |
| 线程池上限 | 15 | `ProcessState.cpp:49` | `setThreadPoolMaxThreadCount(N)`，N ≥ 31 适合 surfaceflinger / 输入分发 |
| ioctl 合并 | 单次双向 | `IPCThreadState.cpp:1246` | 无需调，应用层避免频繁手动 `flushCommands` |
| sync/oneway 选择 | 视接口语义 | `IPCThreadState.cpp:921` | 高频 fire-and-forget 必选 oneway + 检查 `BR_ONEWAY_SPAM_SUSPECT` |
| oneway spam 检测 | 默认开启 | `ProcessState.cpp:555` | `enableOnewaySpamDetection(false)` 仅诊断时禁用 |
| frozen 错误码 | 默认 FROZEN_OBJECT | `IPCThreadState.cpp:1212` | 通过 `android.os.binder.flags.enable_frozen_object_error` 系统属性切换 |

## 性能影响

1. **高频 IPC 场景（如 InputDispatcher ↔ InputReader）**：默认 15 线程是 system_server 全局共享的瓶颈；surfaceflinger 需要单独上调
2. **大 Parcel 场景**：超过 `binder::kLogTransactionsOverBytes`（`Binder.cpp` 内常量）会触发 `ALOGW`，但不阻塞——大 Parcel 占用 mmap buffer 比例大，容易触发 `ENOSPC`
3. **慢事务监控**：`BBinder::transact` 内置 `transactionMs > 1000` 自动 `ALOGW`（`Binder.cpp:579-585`），是服务端定位慢调用的稳定钩子
4. **oneway 滥用**：`BR_ONEWAY_SPAM_SUSPECT` 是 ALOGE 级别日志 + CallStack，可直接定位问题进程
