| 2075435834581668088 | yibie |  | 推荐这篇文章，Armin Ronacher（Flask、Jinja2 作者）写了一篇他自称"想得太多"的深度文章，讨论 Agent 之上正在长出第二层 loop——"harness loop"。不是人在 prompt 模型，而是人写 loop，loop 去跑模型。Armin 的矛盾在于：他既看到这个模式不可阻挡，又对产出"像有机体而非确定性机器"的软件感到不安。这是一篇非常诚实的工程文化文章，没有 hype，只有一位资深工程师面对新时代的思考。

即将到来的 Loop

我不再 prompt Claude 了。我运行 loop，让它们去 prompt Claude、自己判断下一步做什么。我的工作是写 loop。

— Boris Cherny

过去几个月，我看到越来越多的人在 coding agent 之上构建了一个和"直接使用 coding agent"本质上不同的东西。不管这发生在 Pi 上还是其他工具上，模式都是一样的：工作被放入某种队列，机器接走、尝试、停止，然后某个 harness 决定那是否真的结束。如果不是，harness 继续同一个 session、注入另一条消息、用一个修改过的上下文启动新 session，或者把任务发给另一台机器。任务在模型自己会说"我做完了"的那个点之后仍然活着。

这个 loop 我想得比我愿意承认的要多。

我不是很擅长这个——目前

我现在对这种工作方式在我在意的代码上还不太成功——而我在意的代码还挺多的。

一部分是品味，一部分是控制。我对自己写的代码应该长什么样设了高门槛，而且我想理解我交付的代码。在压力下，或者和另一个人类的讨论中，我要能解释这个系统在做什么，而不需要先让一个 clanker 解释给我听。当然，这里有一个问题——几年后我是否还会保留这种理解代码的欲望。但目前我还没越过"理解仍然重要"这条线。

带着这个欲望，我对那些在我注意力缺席时写出的代码——尤其是来自 loop 的代码——总感觉缺少了什么。现在的模型倾向于产生过于防御性、过于复杂、过于局限于局部推理的代码。它们避免强不变性。它们添加回退方案而不是让坏状态变得不可能。它们重复代码、发明糟糕的抽象、用更多机器来掩盖不清晰的设计。更糟的是：我目前几乎没有看到这个情况在改善。甚至在我的品味看来，我们可能在朝错误的方向迈步。比如现在的 Claude Code 配合 Fable 在 ultracode 模式下，产出的代码比去年秋天我们写出的更差。因为 Claude Code 配合 Fable 会不受打断地在一个问题上工作三十分钟或更久，而以前这个过程会有更多人在 loop 里。

此外，人们已经充分理解模型倾向于观察某个局部失败，然后添加一个局部防御。Karpathy 提过它们"极度恐惧异常"。在有重要不变性的系统中——特别是持久化数据格式或核心基础设施——正确的修复不是"处理所有畸形情况"。正确修复是让畸形情况变得无法表示或无法写出。但即使有大量手动引导，那种代码不会从 LLM 中自然产生。即使那种代码自然产生了，它们还是会尝试处理现在已经是不可发生的错误。

当你把这种行为和 loop 结合，你就会放大它。如果每次迭代又加一个小防御，系统慢慢变得不那么可理解，同时看起来更健壮——你越放手，就越这样。当这种工具被交给没有清晰指导的初级开发者时，问题更严重。因为如果你问他们为什么这么做，他们会有说服力地论证他们的理由。

Loop 在什么地方有效

同时，假装 loop 模式不有效是不诚实的，因为它在某些领域已经惊人地有效。

代码移植是其中之一。已经有令人印象深刻的大型自动移植成果，包括将 Bun 的某些部分从 Zig 移植到 Rust。我自己也用这方法成功将 MiniJinja 移植到了 Go。性能探索是另一个表现漂亮的场景。一台机器可以尝试实验、基准测试它们、丢弃失败、继续搜索。安全扫描天然适合，几乎任何类型的研究也是如此：让系统探索一个复杂的问题空间然后汇报，不必产生持久的代码。这些的共同点是：要么不产生新代码，而是转换已有代码，要么产生的代码刻意没有长生命期。它们要么产生概念验证或想法，要么暴露发现，要么更像机械转换。

我认为，产生不需要长期存活的制品或某种形式可验证的机械翻译的 loop，比 harness 机械地衡量某个目标的一般能力更重要。很多成功的 loop 应用是用另一个 LLM 作为评委或编排者。机械翻译的场景可以用二元测试来验证，但也可以用 LLM 来评判。

Claude Code 越来越擅长创建完整的实验工作流然后执行它。当然，它产生的代码是 slop，但这更多是模型的问题，而不是 harness 没办法判断工作流中的某一步是否产生了净改善或完成。harness 只需要一些信号来让它继续。

我特别喜欢那些把无聊的部分从我的日常工作中去掉、让我做实验和测量然后给我想法的 loop。

软件作为有机体

但另一方面，用同样的 loop 方法论来写持久化代码，我目前还接受不了。我喜欢用的比喻是从"作为确定性机器的软件"转变为"作为有机体的软件"。

我成为一名软件工程师的环境鼓励我去理解机器。总是有一层可以揭开，来加深理解。没有展现出确定性可观察行为的机器可能被接受，但通常被认为不理想。在软件架构上，我认为向往更多确定性而非更少是值得的。同样，理解代码的能力一直是一个不可否认的目标。在实践中不总是可能，但我们仍然为写出能让新工程师也能在复杂代码库中导航的代码而感到自豪——通过巧妙的架构。在一个设计良好的系统中，总是有工程师知道不变性在哪里、哪些部分承重、哪些变更是安全的。理想情况下，这些都有文档。如果缺乏，一般被认为是需要改善的事情。

显然这个理想一直承受着压力。许多软件系统——尤其是特别成功的那些——有过团队内部工程师能够保持它们干净的时期。大型软件系统经常太大、太动态、太依赖外部服务，以至于不适合任何人的头脑。即使没有 LLM，我们已经在像医生一样诊断分布式系统：观察症状、形成假说、"再开一些检查"、尝试一些治疗、再观察。

但是有了 LLM，我们在朝那个方向走得更快、更远。我们用它们来写代码，也用它们来诊断和治疗。已经有大量的工程师活在这样的世界里：生产环境出现问题后，第一步是让一个 clanker 读日志、提出根因、主动提交 patch。生成的 patch 经常被另一台机器审查，有时甚至在没有人类监督的情况下合入主分支。

显然这很强大，我无法否认。但接受这个想法——尤其是在越来越少人类监督的情况下——意味着接受我们可能不再以同样的方式理解整个系统。我们治疗它，监控它，稳定它，但我们不一定理解它。

我毫不怀疑对某些软件来说，这是可以的。不是每一行代码都值得人类执笔，而且更差的代码在过去也被写过。

但我想所有软件都这样被创造吗？

你无法真正选择退出

非常不舒服的是，从这个完全机器驱动的未来中选择退出可能不是一个选项。

安全是今天最清晰的例子。即使你不在 loop 中构建你的软件，别人会在 loop 中针对你的软件。攻击者会持续运行机器——即使不是攻击者，安全研究人员也会——一些自动化工作会扬尘但也会发现真正的问题。信号和噪音都会以超过你能人工处理的体量流向你。

Daniel Stenberg 关于 curl 的"夏日快乐"的博文就是维护者已经承受的压力的一个好例子。人工智能在 curl 核心开发中还没有扮演什么角色。但尽管如此，维护者已经被报告淹没，其中大部分报告都是 AI 生成的。

如果攻击者和报告者在 loop，防御者最终也需要 loop 才能跟上。也许不是直接写 patch，也许只是做 triage 和复现。压力会增长。

竞争上同样如此。有些团队会通过原始速度超出其他团队。一些项目会突然移动得更快，因为一个小群体弄清楚了如何有效编排机器。一些创业公司用五个人做出以前需要五十个人的东西。有些人真的会放一台机器在 loop 中针对你的产品，让它"做出另一个一样的东西"。如果他们的用户满意，这真的重要吗？

建立新的依赖

对我来说最可怕的部分是，我们以新的方式变得依赖这些新机器。软件一直依赖工具。我经历过必须花钱买编译器的时代。这些新工具是回到那个时代的闪回——那个创造软件伴随着真实成本的时代。但现在这不再是一次性支付，而是一个持续的依赖。不只是在钱包上的依赖，更是一种认知依赖。

如果一个代码库是由 loop 产生的，由 loop 审查的，由 loop 修补的，由 loop 维护的，那么当你不再有权限访问同一类系统时会发生什么？当贸易限制剥夺了使用最强大模型的机会？如果仅仅是成本变得无法承受？如果你和你的团队刚好失去了最后一个不用机器理解代码的能力？

我们可能创造出不只是人工难以维护的代码库，而是把机器参与当作维护模型一部分的代码库。这已经在发生了！不是到处发生，可能甚至没有被视作问题，但我们看到越来越多这样的情况。人们越来越多合并那些他们无法充分解释的代码。人们失去在没有 clanker 提供上下文的情况下创建问题报告或讨论的能力。太多人越来越依赖机器来做摘要或提供上下文。我越来越多地遇到通过 LLM 间接与我交流的人。

再说一次，也许这不会是错的，但这对于我们做事的方式是一次巨大的改变。

未来的 Harness

我毫不怀疑这就是发展方向。但走向那需要我们对工具进行全方位的改进，而不只是在 coding agent 上。

仅仅编排更多 loop 是不够的。更好的变更可视化、更好的编排或 agent 并不会恢复我们的理解能力。要么我们需要找到聪明的方法把人弹回 loop 里，让 loop 的变化对其长期可读；要么我们需要找到更好的方法来组合这些越来越复杂的系统。

这也是我对 Pi 角色的思考正在改变的地方。Pi 一直很谨慎，我认为这种谨慎是好的。我不想要一个未来中，每次交互都变成一个不可控的机器蜂群，产生我看不懂的变化。我不希望 Pi 在竞争中为了赢得"自我编写软件"的竞赛而变成一个无法维护的烂摊子，我也不希望 Pi 推崇这种工程方式。同时，在这些新型实验中 Pi 是一个 harness，而 harness 处于人们运行这些新型实验的核心。

编码任务的任务队列、Agent 编排、子 agent、持久 session——这些将变得越来越重要。即使那些有疑虑、没有盲目拥抱 loop 的人，也不得不开始做这些实验。我们必须做，因为我们需要理解如何让这个未来有边界、可生存。

控制 Loop

正如你能从这篇文章中读出的，我对这个未来非常不安。不是因为恐惧，而是出于谨慎——基于到目前为止和这项技术的打交道的经验。

拥抱 harness loop 的理念意味着 harness 来决定工作何时完成。在 agent loop 中，模型最终说"完成了"，然后我审查。在那之前，我通常在过程中指引导。我参与了，享受了过程中的学习。在 harness 操作的 loop 中，我甚至不确定我的角色是什么。连"完成"信号都失去了所有含义，只是被传达给另一个机器来评判。我的角色变成了一条传话筒。

今天我不喜欢从这种系统中看到的大多数代码，我也不喜欢和有大量 AI 辅助的软件交互。Loop 的力量很大，但它越来越多的消除责任，至少在今天，它非常鼓励我们屈服于机器。

然而我毫不怀疑这个 loop 未来将是我们的未来——尽管我现在仍然对它感到反感。我已经看到惊人的小团队以不可能的速度构建，我看到代码库越来越多地变成晦涩的、混乱的有机体——只有更多机器才能诊断它们。这些代码库同时有用而混乱。

所以我想我正在想通的一点是：问题不是"我们会不会 loop"——因为我们显然会。也许问题是：在这个 loop 的未来里，我们如何不放弃判断力，如何保留好的工程规则，如何确保负责任的人能持续监督，以及如何在架构代码时保留这个过程中残留的理智。
