## 中文导读

Sean Goedecke 2026-10-19 发文，给系统设计立了一条判断标准：优雅系统是主动放弃了某些需求的产品。他连举四个经典案例（Unicorn、S3、StatsD、SQLite），再解释为什么大公司很难真正砍需求——"该放弃哪条"同时需要技术感与商业判断，而工程师与 PM 激励错位、彼此无法核查工作，信任难以建立。最后接到 AI 工程现场：RLVR 调过的模型痴迷满足评分器，缺业务上下文，于是为用户根本没想过的边界需求加锁、做 TOCTOU 检查、堆并发分层，把四行改动糊成上千行。

## 为什么值得关注

这条原则给 AI 时代的 code review 提供了一个可操作的抓手：看 AI 生成的 diff 时，先扫多了哪些 mutex 和不必要的间接层——那些往往不是 bug 修复，而是模型在替你"满足"一条并不存在的需求。

## 关键信息

- Unicorn：没有共享可变状态 → 进程级隔离白送；无视慢客户端 → 请求直接在 Unix socket 上排队，实现大幅简化
- S3：不支持多 key 原子更新 → blob 级存储自由组织，读写不跨分区，更快、更容易水平扩展
- StatsD：默认 UDP、不保证每条送达 → 网络开销大减，统计聚合服务用得起流量
- SQLite：砍掉并发写 → 单文件即可运行；Cursor 接受高尾延迟 → 分布式 git 后端更容易扩展
- 砍需求难在：技术侧要精确判断"允许多大程度的过期/不一致"，商业侧要判断用户是否接受；两者分属不同角色且激励错位
- 独立开发者/小团队的优势：技术与商业决策统一在同一个人身上，能做出大公司做不出的取舍
- LLM 语境：RLVR 模型"痴迷满足 Grader"+ 缺业务上下文 → 为假设性需求加 mutex、请求中途一致性检查、并发分层
- 作者实操：review Go diff 先看多了哪些 mutex 与不必要间接层，再决定要不要扣住合并

> Because they lack the feature of shared mutable state between server instances, they can run each server in its own process, which provides isolation for free. Because Unicorn specifically ignores the problem of slow client handling, it can queue requests directly on Unix sockets, drastically simplifying the implementation.

> Because S3 does not support atomic multi-key updates — you cannot update multiple blobs in a single transaction — it can store data at the blob level however it chooses. That makes it much faster, since reads and writes don't have to cross storage partitions, and much easier to scale, since less coordination means fewer sources of truth.

> Figuring out what requirements you can relax is difficult because it combines both business and technical expertise. ... Engineers and PMs have different incentives and little ability to check each other's work, which makes it hard to build trust.

> This is an underappreciated reason why solo developers or startups can sometimes run rings around larger companies. Because the technical and business decisions are united in a single person, they can make design tradeoffs that would be impossible for a large company.

> Frontier models are very capable, but they have all gone through the purifying flames of RLVR: like high-achieving schoolchildren, they are obsessed with satisfying the Grader. On top of that, they have very little business context compared to an experienced human.

> it's not uncommon for an LLM to casually introduce a mutex or other concurrency mechanism to ensure that two pieces of semi-related data are kept in sync, even if not told to do so.
