# 源码调研：Android 17 高精度内存跟踪库 libmeminfo 源码深度解析

📅 2026-06-22 | AIW · 每日源码调研

## 盲区来源

- **关联章节**：§26.14 Android 内存跟踪 API 集成与性能可观测性（ch26-observability/26.14）
- **每日选题 ID**：1（high 优先级）
- **原选题价值**：填补 Android 系统级内存监控的技术断层，提供高精度内存跟踪 API 替代方案
- **现状问题**：现有 §26.14 章节内容存在大量**未经一手验证**的类/方法名（如 `MemoryTrackable` 接口、`MemoryCategory` 枚举、`MemoryPressureDetector` 类），源码中并不存在这些符号；真实的高精度内存跟踪能力由 AOSP 原生库 `libmeminfo`（C++）提供，通过 JNI 暴露给 Java 层 `android.os.Debug` 与 `android.app.ActivityManager`。

## 核心发现

Android 17 的高精度内存跟踪由三块构成：

1. **基础统计库 `libmeminfo`**（C++，`system/memory/libmeminfo`），提供 `ProcMemInfo`（per-process 维度的 VMA/Pss/Uss/Rss/WSS 统计）和 `SysMemInfo`（system 维度 `/proc/meminfo` 解析、zram 读取、vmalloc 统计）。它不依赖 binder/HIDL，进程内同步调用即可。
2. **高精度扩展 `libmemevents`**（C++，同目录，2023 年新增），通过 **eBPF ring buffer** 监听内核 tracepoint（`oom/mark_victim`、`vmscan/mm_vmscan_direct_reclaim_*`、`vmscan/mm_vmscan_kswapd_*`、`android_vendor_lmk/...`、`kmem/mm_calculate_totalreserve_pages`），将 OOM kill、direct reclaim、kswapd wake/sleep、vendor LMK kill、zoneinfo 更新等事件实时推送给 `MemEventListener`，是「实时内存压力指标」的真实实现路径。
3. **Java 入口**：`android.os.Debug.getMemoryInfo()` 与 `ActivityManager.MemoryInfo` 通过 JNI（`frameworks/base/core/jni/android_os_Debug.cpp`）调用 `ProcMemInfo::SmapsOrRollup` / `StatusVmRSS` 与 `SysMemInfo::ReadMemInfo`。

**重要纠偏**：§26.14 中提到的 `MemoryTrackable` 接口、`MemoryCategory` 枚举、`MemoryTracker` 类、`MemoryPressureDetector` 类在 AOSP 源码中**均不存在**，属于早期草稿的占位/虚构内容，本调研报告以真实源码重写核心 API 描述。

### 2. 核心数据结构（`include/meminfo/meminfo.h`）

```cpp
struct MemUsage {
    uint64_t vss;          // virtual set size
    uint64_t rss;          // resident set size
    uint64_t pss;          // proportional set size
    uint64_t uss;          // unique set size
    uint64_t swap;
    uint64_t swap_pss;
    uint64_t private_clean, private_dirty;
    uint64_t shared_clean,  shared_dirty;
    uint64_t anon_huge_pages, shmem_pmd_mapped, file_pmd_mapped;
    uint64_t shared_hugetlb, private_hugetlb;
    uint64_t locked;
    uint64_t thp;          // transparent huge pages
    ...
};

struct Vma {
    uint64_t start, end, offset;
    uint16_t flags;
    std::string name;
    uint64_t inode;
    bool is_shared;
    MemUsage usage;        // 该 VMA 的内存使用
};
```

这套结构直接对应内核 `smaps` 输出，是 Pss/Uss/Rss 的 C++ 表达。

### 3. ProcMemInfo 类的两条采样路径

**路径 A：`SmapsOrRollup` 走内核 rollup（快路径）**

`procmeminfo.cpp:336-338`：

```cpp
bool ProcMemInfo::SmapsOrRollup(MemUsage* stats) const {
    std::string path = ::android::base::StringPrintf(
        "/proc/%d/%s", pid_, IsSmapsRollupSupported() ? "smaps_rollup" : "smaps");
    return SmapsOrRollupFromFile(path, stats);
}
```

`smaps_rollup` 是 Linux 4.14+ 引入的内核优化（`fs/proc/task_mmu.c`），只需一次 read 就能拿到整个进程聚合的 Pss/Private_Clean/Private_Dirty，**避免逐 VMA 解析**。`IsSmapsRollupSupported()`（`procmeminfo.cpp:658-676`）使用 `std::atomic<smaps_rollup_support>` 做线程安全缓存：先 access `/proc/self/smaps_rollup` 一次，结果在 `g_rollup_support` 里 atomic 共享——`memory_order_relaxed` 即可，因为只用于「能力探测」，不影响正确性。

**路径 B：`ReadVmaStats` 走 pagemap/kpageflags/kpagecount（高精度路径）**

`procmeminfo.cpp:466-575`，关键调用链：

1. `GetPagemapFd(pid_)` 打开 `/proc/<pid>/pagemap`
2. 2048 页分块（`kMaxPages = 2048`）批量 `pread64` 读 page frame number
3. 通过 `PageAcct::PageFlags(pfn, &flags)` 查 `/proc/kpageflags`
4. 通过 `PageAcct::PageMapCount(pfn, &count)` 查 `/proc/kpagecount`
5. 用 `KPF_REFERENCED` 或 `PageAcct::IsPageIdle(pfn)` 判定 WSS
6. 计算：
   ```cpp
   bool is_private = (cur_page_counts == 1);
   vma.usage.pss += pagesz_kb / cur_page_counts;  // 关键: 按映射数分摊
   if (is_private) vma.usage.uss += pagesz_kb;
   ```

精度优势：相比 `Debug.MemoryInfo` 只取 `Pss`/`PrivateDirty` 等聚合值，`ReadVmaStats` 能按 VMA 维度输出，并支持 working set（`get_wss=true` 时启用）、swap offset（`collect_swap_offsets=true` 时返回每个被换出页的 swap 偏移）等精细信息。

### 4. PageAcct 单例与 idle page tracking

`pageacct.cpp:55-89`：`PageAcct::InitPageAcct(bool pageidle_enable)` 打开三件套：

- `/proc/kpagecount`：获取每页被多少进程映射
- `/proc/kpageflags`：获取每页 flag（Dirty、Referenced、THP 等）
- `/sys/kernel/mm/page_idle/bitmap`（`pageidle_enable=true` 时）：内核 idle page tracking

`PageAcct::IsPageIdle`（`pageacct.cpp:118-127`）通过 `pwrite64` 设置 bitmap bit，再 `pread64` 读出上次标记后的访问情况。这是 Linux 内核 `CONFIG_IDLE_PAGE_TRACKING` 的标准用法，精度比单看 `KPF_REFERENCED` 高（Referenced 可能在两次采样之间被清掉，page_idle bitmap 是显式时间窗标记）。

### 5. SysMemInfo：`/proc/meminfo` 解析器

`sysmeminfo.cpp:65-93`：`ReadMemInfo` 一次性读取 4KB buffer，遍历 `kDefaultSysMemInfoTags` 列表（30 项：`MemTotal`、`MemFree`、`Buffers`、`Cached`、`Shmem`、`Slab`、`SReclaim`、`SUnreclaim`、`SwapTotal`、`SwapFree`、`Mapped`、`VmallocUsed`、`PageTables`、`KernelStack`、`KReclaimable`、`Active`、`Inactive`、`Unevictable`、`MemAvailable`、`Active(anon)`、`Inactive(anon)`、`Active(file)`、`Inactive(file)`、`CmaTotal`、`CmaFree`、`SwapCached`、`SecPageTables`、`Percpu`）。`Zram:` tag 通过 `mem_zram_kb()` 单独计算（`sysmeminfo.cpp:155-185`），扫描 `/sys/block/zram0..255/mm_stat` 或旧的 `mem_used_total`。

**ZRAM compaction**（Android 14 引入）通过 `mem_compacted_kb()` + `GetTotalMemCompacted()`（`sysmeminfo.cpp:241-262`）从 `mm_stat` 解析 `uncompressed_size - compressed_size`，得到「真正因 zram 节省出的内存」。

### 6. libmemevents：基于 eBPF 的实时内存事件

**这是 §26.14「实时内存压力指标」的真实实现路径。** 关键源码 `libmemevents/memevents.cpp:50-141`：

```cpp
static const std::vector<std::vector<struct MemBpfAttachment>> attachments = {
    // AMS
    { { .prog = "..."_OOM_MARK_VICTIM_TP,
        .tpGroup = "oom", .tpEvent = "mark_victim",
        .event_type = MEM_EVENT_OOM_KILL } },
    // LMKD
    { { .prog = "..._VMSCAN_DR_BEGIN_TP",
        .tpGroup = "vmscan", .tpEvent = "mm_vmscan_direct_reclaim_begin",
        .event_type = MEM_EVENT_DIRECT_RECLAIM_BEGIN },
      { .prog = "..._VMSCAN_DR_END_TP", ... },
      { .prog = "..._VMSCAN_KSWAPD_WAKE_TP", ... },
      { .prog = "..._VMSCAN_KSWAPD_SLEEP_TP", ... },
      { .prog = "..._TRIGGER_VENDOR_LMK_KILL_TP",
        .tpGroup = "android_vendor_lmk",
        .tpEvent = "android_trigger_vendor_lmk_kill",
        .event_type = MEM_EVENT_VENDOR_LMK_KILL },
      { .prog = "..._CALCULATE_TOTALRESERVE_PAGES_TP",
        .tpGroup = "kmem",

        .event_type = MEM_EVENT_UPDATE_ZONEINFO } },

```

事件类型定义在 `bpf_types.h:25-35`：

```c
#define MEM_EVENT_OOM_KILL              0
#define MEM_EVENT_BASE                  MEM_EVENT_OOM_KILL
#define MEM_EVENT_DIRECT_RECLAIM_BEGIN  1
#define MEM_EVENT_DIRECT_RECLAIM_END    2
#define MEM_EVENT_KSWAPD_WAKE           3
#define MEM_EVENT_KSWAPD_SLEEP          4
#define MEM_EVENT_VENDOR_LMK_KILL       5

#define NR_MEM_EVENTS                   7
```

数据结构 `struct mem_event_t`（`bpf_types.h:60-87`）使用 union 携带事件数据：

- `OomKill { pid, timestamp_ms, oom_score_adj, uid, process_name[16], total_vm_kb, anon_rss_kb, file_rss_kb, shmem_rss_kb, pgtables_kb }`
- `KswapdWake { node_id, zone_id, alloc_order }`
- `KswapdSleep { node_id }`
- `VendorKill { reason, min_oom_score_adj }`
- `TotalReservePages { num_pages }`

调用链：

1. `MemEventListener::registerEvent(MEM_EVENT_KSWAPD_WAKE)`（`memevents.cpp:240-273`）
2. 找到 `MemBpfAttachment`，调 `retrieveProgram(prog_path)` 拿 BPF prog fd
3. `bpf_attach_tracepoint(fd, "vmscan", "mm_vmscan_kswapd_wake")` 挂到内核 tracepoint
4. `MemEventListener::listen(timeout_ms)`（`memevents.cpp:294-303`）阻塞在 `memBpfRb->wait(timeout_ms)`（BpfRingbufBase）
5. 内核 tracepoint 触发 → BPF prog → BPF ring buffer → 用户态消费

**内核版本要求**：`isAtLeastKernelVersion(5, 8, 0)`（`memevents.cpp:48`），因为 BPF ring buffer（`BPF_MAP_TYPE_RINGBUF`）是 Linux 5.8 引入。Android 17 设备的 kernel 普遍 ≥ 5.10，所以这个能力普遍可用。

### 7. JNI 入口：Java → libmeminfo

`frameworks/base/core/jni/android_os_Debug.cpp:288-307`（`android_os_Debug.cpp` 共 906 行）：

```cpp
::android::meminfo::ProcMemInfo proc_mem(pid);
::android::meminfo::MemUsage stats;
if (proc_mem.SmapsOrRollup(&stats)) {
    pss += stats.pss;
    uss += stats.uss;
    rss += stats.rss;
    swapPss = stats.swap_pss;
    pss += swapPss;  // swap 中的页若不交换会算作 Pss
}
```

`android_os_Debug.cpp:430-465` 的 `read_system_mem_info` 用 `SysMemInfo::kDefaultSysMemInfoTags` 把所有 tag 一次性读到 `std::vector<uint64_t>`，再拷给 Java `long[]`。**注意** Android 17 在 `MEMINFO_ZRAM_TOTAL` 位置插入 `"Zram:"` tag，这是 zram 内存进入 `ActivityManager.MemoryInfo` Java API 的桥接点。

`/proc/self/smaps_rollup` 探测在 JNI 端也有一份（`android_os_Debug.cpp` 中 `OpenSmapsOrRollup`），与 `libmeminfo::IsSmapsRollupSupported` 互相配合——这是 §26.14 「`Debug.MemoryInfo` 升级到 `smaps_rollup`」的真实实现机制。

## 性能影响

`libmeminfo` 自身开销分布：

1. **`SmapsOrRollup` 路径**：单次 read 聚合文件，开销 ≈ 一次 syscall + 文本解析，量级 **O(KB) 内存 / O(100µs) 时延**（具体取决于进程 VMA 数）。Java 层 `Debug.getMemoryInfo()` 推荐走这条。
2. **`ReadVmaStats` + pagemap 路径**：每 2048 页一批 `pread64` pagemap + 每页两次 `/proc/kpageflags` & `/proc/kpagecount` `pread64`，**单次全量扫描可触发数十万次 syscall**。在生产环境使用必须：
   - 限频（≥ 5s 间隔）；
   - 仅在 `get_wss=true` 时按需打开 `/sys/kernel/mm/page_idle/bitmap`；
   - 通过 `pgflags`/`pgflags_mask` 过滤（如只统计 anonymous+swap）减少 page flag 查询。
3. **`libmemevents`** 路径：BPF prog 在内核态直接 attach，无持续开销；事件到来时通过 ring buffer 异步通知，**AMS 端监听 overhead 接近零**。这是 §26.14 「实时内存压力指标」应当推荐的实现。
