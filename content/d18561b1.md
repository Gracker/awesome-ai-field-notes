## 中文导读

宝玉 11-20 整理 Anthropic 11-18 分享：Claude Code 约 90% 代码由 Claude 写，日进仓改动 5 月 2500 → 9 月 3 万+，6–9 月合入 PR 翻倍而回滚比例反降 40%+。最硬一步：把真实引发事故的 PR、修复与回滚做成考题，工程师确认 bug 位置，智能体回到当时审查，按召回率与精确率衡量；实质审查意见覆盖率 16%→54%。收敛教训：一个 CLI PR 跑 50 多轮才被掐停，blame 显示 59% 是首轮旧代码；调法是三轮后重想方案、只审新增 diff、不重复提报。风险分级由分类器读改动定签字人数，与提交者无关；定价按 token，预览期 15–25 美元/次。

## 原帖摘录（opencli twitter article 存档）

Claude Code 团队是如何做代码审查的？
https://t.co/2J6JYFX8HF

“Clark，你给我的 PR 盖章，我就给你的盖章。”

这是半年多前 Anthropic 内部的日常。Claude 写代码越来越快，等人审的改动排成长队，大家只好互相放行，看是谁提交的，扫一眼就批准。

Claude Code 团队的产品经理 Morgan Lunt 在这场分享里把那段时间叫作“歌舞伎表演”，审查的形式还在，其实大家只看了个大概。

后来他们让 AI 智能体接手了绝大部分审查，人只在少数高风险改动上签字。目标是 90% 的 PR 合并时，除了让 Claude 干活的那个人，不需要再找任何人。

Lunt 给出的结果是：改用自动审查后，查出实质问题的 PR 比例从 16% 升到 54%，合并的 PR 数量又翻了一倍，需要回滚的 PR 少了 40%。在他看来，这和自动驾驶是一个道理，用不着完美，比人强就够了。

瓶颈从写代码转到了审代码

PR（拉取请求）是程序员提交一份代码改动、请别人检查后再合并进主代码的流程。Lunt 说，一年前 Anthropic 和别的公司一样，几乎每个 PR 都由人来审，代码产出的速度就是人写代码的速度。

大约九个月前，模型强到可以独立做完一个功能，大家开始直接把任务丢给 Claude，产出一下子多了很多，审查就成了最慢的环节。他引用了一项哈佛的研究：企业引入 AI 编程智能体后，PR 等待审查的时间平均增加了 56%。他读那篇论文的理解是，PR 太多，人被淹没了。

Anthropic 的工程师擅长做智能体，于是很多人各自写了审查机器人，把自己审代码时关注的点写进去。结果一个 PR 上会出现七个机器人，意见互相冲突，一个机器人要的改动会惹另一个机器人不满，来回改出五十、一百甚至两百次提交，改到最后已经偏离了作者原本想做的事。

问答中他解释，冲突的原因是各个机器人关注的方向不同，有的对接口怎么设计要求很细，有的不管，而它们之间没有共享的上下文和共同的目标。他们后来把这些机器人的关注点合并进一个主审查智能体，由它在内部去重、整理。

大约今年 7 月，Claude Code 的创建者 Boris Cherny 找到 Lunt 的团队，让他们“把 Anthropic 的代码审查问题解决掉”。

团队给自己定的目标就是开头说的 90%，并按需要几个人参与把 PR 分成三类：零人参与，是 Claude 自己发现问题、自己修、自己提交、自己盯到合并；一人参与，是某个人让 Claude 做了一件事，自动系统判断没问题就直接合并，不用再找人；两人及以上，留给账单、用户登录验证、应用自动更新这类绝对不能出错的地方，而且范围尽量收窄。

同时有一条底线：回滚、紧急补救和线上事故都不能因此变多。

用自己出过的事故来检验审查

要知道审查智能体好不好，得有一套考题。他们把 Anthropic 历史上所有线上事故，以及被认定引发事故的那些 PR 整理成评测集，再请人抽查核对，没有用人为埋了 bug 的合成数据。这样考的都是在自家代码上真实出过问题的情况。

每道题的格式很简单。Lunt 现场展示了一个例子：某个 PR 合并后有客户收到了两次同一张发票，只好回滚，原因定位在某个文件的第 88 行。这道题记录的就是代码仓库在那个时间点的版本号、PR 编号、出问题的文件和行号，以及正确答案。成千上万道这样的题，就是评分标准。审查智能体被放回那个时间点去审那个 PR，看它能不能找到那一行。

衡量时看两个数。一个是召回率：标准答案里列出的问题，它找到了多少。另一个是精确率：它报出的问题里，有多少是标准答案之外、大概率不该报的。只看召回率不行，因为让智能体随便报五十万条，迟早会撞中所有答案，但真正有用的提醒就淹没在噪音里了。

在这套考题上，他们试了不同的提示词，不同的检查角度（比如专门找某类安全漏洞，或者专门找“同一个操作执行两次会不会出错”这类问题），以及不同的智能体分工结构，跑了几万到几十万次。方法就是反复试：改一处，成绩变好就留下，变差就扔掉。Lunt 说 Claude 让同时跑大量实验变得很容易。

最后定下来的流程是：先派出一批负责找问题的智能体，再派出一批负责“挑刺”的验证智能体，专门质疑前者的发现，确认是真问题；然后按严重程度排序、去重，作为评论贴到 PR 上。发现分三档：重要问题会阻止合并；小问题（nit）不阻止，留着以后想集中清理时再翻；还有一档是改动之前就存在的老问题。完全无关紧要的，在验证阶段就被删掉。

让找问题的智能体适可而止

Lunt 说他为“收敛”这件事钻研了三个星期。智能体被要求找问题就一定会找到问题，被要求修问题就一定会去修。让一个智能体找问题、另一个修，再问前一个“现在怎么样了”，它会接着找出越来越偏门、越来越鸡毛蒜皮的毛病。有段时间，智能体整夜来回找、修，一个 PR 上积累几十上百次提交，偏离用户的原意，也没人看得懂。

他们的调法是让审查智能体一次把所有发现都报出来，修完之后不再越挖越深。他说现在九成多的 PR 在三轮“审查、修复”之内就能收敛，但为此在提示词上花了不少功夫。

哪些改动还需要人看

审查之后还有一步风险分级，由一个机器人根据 PR 改了哪些文件、改了多少来决定要几个人批准。只改文档、影响面小的，直接通过；普通改动，让 Claude 干活的那个人负责就够了；涉及账单、自动更新这类高风险部分，要第二个人签字。

他们最早用的是“代码负责人”配置文件，按文件路径规定某个目录下的改动需要一个人还是两个人批准。Lunt 说这个办法太粗，后来又加了一层由大模型做的判断。比如账单相关的代码，如果改动涉及业务逻辑，就要另一个人签字，如果不涉及就直接放行。

他演示的三个例子是：修改安装指南里的错别字，不需要额外审查；给订单列表加一个日期筛选，需要一个人，因为碰到了订单；改发布流程，要发布团队的人点头，因为影响面大。权限也按团队分，他在 Claude Code 代码仓库里能做的事，其他团队的人不一定能做。

整条流程他称为六层：Claude 写代码的同一个会话里先自己跑测试、修失败、再派一个上下文干净的子智能体复查；PR 提交后由托管的 Claude Code Review 做深度审查；再过一遍安全审查；然后是常规的自动检查和测试；只有真正需要的 PR 才找人批准；最后合并。

他把这叫作“瑞士奶酪”式的防护，每一层都有漏洞，叠在一起就很难漏过去。此外，Anthropic 的产品大多通过网页和自己控制的 App 发布，新功能上线默认是关着的，先开给少量内部测试者，再开给更多外部测试者，最后才全面开放。出了问题，几分钟内就能对所有人关掉，不用改代码。

审查发现问题之后，修复也要自动化。Lunt 说内部有人用 Claude Tag，有人自己写了“盯 PR”的技能，让写这个 PR 的 Claude 会话定时去 GitHub 看有没有审查意见要处理。他的理由是，修复如果还要等人醒着、有空，提速就无从谈起。

问答中，团队的工程师把审查要回答的问题分成三层：最底层是代码风格和整洁程度；中间一层是假设这个改动的方向是对的，它写得对不对、安不安全；最上层是这个功能该不该做、方向对不对。自动审查擅长的是中间这层，最上层留给人。Lunt 补充说，他们刻意不让审查智能体管得太宽，不会因为它觉得不妥就拦住你明确要做的事，所以防止有人往代码库里塞恶意改动，仍然要靠团队自己。

普通团队可以怎么照着做

Lunt 建议想引入自动审查的团队，先用自家的事故记录建一套评测集。大多数公司都有事故追踪系统，让 Claude 从里面提取被认定引发事故的 PR
