1. 把 Fable 5.2 挂成 Claude Code 的顾问模型，周限额面板不动这件事被实测过

@mylifcc 今天上午转了一条 r/ClaudeAI 的实测：主模型照常挂 Opus 5.5，用 /advisor 把顾问模型设成 Fable 5.2，遇到卡壳的架构抉择时在提示词里点名让主模型去请教顾问，多位重度用户对着后台用量面板确认，这条路径触发的 Fable 5.2 推理在统计上对 Fable 5.2 的周限额消耗是 0%，并提醒别等会话上下文快塞满才叫顾问，长上下文一把灌过去容易撞单次速率限制。原帖在 Reddit 上被吵了 9 天，版主机器人在 50 条评论后总结说社区压倒性认为发帖人搞错了，主流解释是 Opus 压根没调用顾问，因为 /advisor 不强制咨询，模型觉得没必要就不调。

另一份独立实测给了不同答案。paddo.dev 11 月 16 日的实验分两步：先在一个 Fable 已经 100% 用满、额外用量关闭的账号上跑 Opus 5.5 加 --advisor fable 并强制触发一次顾问调用，调用成功，API 记录里的模型就是 claude-fable-5-2，41,571 个输入 token；再换一个新账号看计量会不会动，10 次 Fable 顾问调用打在一个 218K token 的上下文上，消耗 218 万未缓存输入 token、6.7 万输出，Fable 周限额面板停在 6% 原地不动，而一小时前一次直接使用 Fable 的同等规模消耗（约 400 万 token、多为缓存）把同一块面板从 3% 推到了 6%。顾问确实被调了，差异出在计费归口。

机制在官方文档里能对上。advisor 是跑在服务端的工具，顾问每次调用都重读一遍完整对话，包含每一次工具调用和结果，顾问自己读的这部分不进缓存，每次调用重新算，所以上下文越大单次越贵；文档也写明没有开关能限制或强制顾问的调用次数。计费上官方写得很清楚：订阅套餐的顾问用量计入套餐额度，Fable 作为顾问时在那些 Fable 本身就走 usage credits 的套餐上同样按 credits 计。Fable 5.2 输入 $8/MTok、输出 $40/MTok，Opus 5.5 是 $4/$20，Reddit 里有条评论按这个单价算过，500K 上下文一次顾问调用约 4 美元输入。配置上 Fable 5.2 在主模型 Opus 5/5.5 的可配对表里，需要 Claude Code v2.1.321 以上，在需要 usage credits 授权的套餐上还得先 /model fable 同意一次。

我的判断：这条技巧换掉的是计数器，额度总量没变。值得带走的是两件事。一是看到 Fable 面板不动时你分不清是真没扣还是顾问压根没被调，paddo 的实验靠强制调用加读 API 记录才确认额度在走，用量面板的截图证明不了什么。二是这条路的性价比完全取决于上下文长度，长会话里顾问每次都要重读全部历史还不吃缓存，最省的做法是尽早在一个干净窗口里问，别攒到会话尾部。真要把 Fable 用过 100% 之后的价值捞回来，社区里更认可的做法是让 Fable 当编排者、把实现交给 Sonnet 和 Haiku，这条路反而更省。
