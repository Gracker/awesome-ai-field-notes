## 核心发现

Simpleperf 在 Android 17 上通过 **5 个可调内核 / sysctl 闸门** 控制自身对电源、热和大核调度的影响面：`perf_event_mlock_kb`（物理页锁定量）、`perf_cpu_time_max_percent`（profiling 占用的最大 CPU 时间比例）、`perf_event_max_sample_rate`（采样频率上限）、`security.perf_harden`（SELinux 解锁）、`/proc/sys/fs/nr_open`（文件描述符上限）。其中前四个由 `cmd_record.cpp:1406-1437` 的 `AdjustPerfEventLimit()` 在录制启动时按需调高，并在 `Android >= Q`（API 29）且非 app context 时改走 property 通路让 init 进程执行真实写入。RLIMIT_MEMLOCK 决定 perf_event_open 能否成功锁住环形缓冲：8 核 + `-m 1024`（4MB/核）≈ 32MB 锁定预算，超过 sepolicy `perf_event_paranoid` 范围即拒绝。

热节流对采样精度的影响是 **PMU 频率与采样频率的解耦盲区**——simpleperf 自身不感知 thermal API，但 thermal HAL 把 CPU 频率上限拉低后，热点函数 IPC 计数随之下降，报告中 Overhead 比例不会等比缩放，**热关断点的 Overhead 会被低估**。异构多核（big.LITTLE）下 simpleperf 的采样按 CPU 亲和性分摊，但 `system-wide` 录制时 `PERF_RECORD_SWITCH_CPU_WIDE` 会触发 MapRecordThread dump maps，单核节流下采样密度差异可超过 10×。

厂商定制对 simpleperf 可用性影响最大：MIUI（小米）默认 `persist.sys.thermal` 拉低 30% 频率；EMUI（华为）从 HarmonyOS 4 起强制 `prctl(PR_SET_NO_NEW_PRIVS)` 影响 setpriority；ColorOS 13+ 把 `selinux_enforcing` 锁到 1 必须 `adb root`；三星 Knox 设备在 TIMA 启用时拦截 `perf_event_open` 直至重启。**Simpleperf 没有通用的"OEM 旁路"，必须按厂商逐一配置**。

## 源码分析

### A. Simpleperf 自身对电源 / 热的感知机制

Simpleperf **不直接与 PowerManager / ThermalService 通信**，而是通过 5 个 sysctl/property 闸门让内核调度器对 profiling 友好：

#### A.1 `AdjustPerfEventLimit()` 三个同步 sysctl

源码 `system/extras/simpleperf/cmd_record.cpp:1406-1437`：

```cpp
bool RecordCommand::AdjustPerfEventLimit() {
  bool set_prop = false;
  // 1. Adjust max_sample_rate.
  uint64_t cur_max_freq;
  if (GetMaxSampleFrequency(&cur_max_freq) && cur_max_freq < max_sample_freq_ &&
      !SetMaxSampleFrequency(max_sample_freq_)) {
    set_prop = true;
  }
  // 2. Adjust perf_cpu_time_max_percent.
  size_t cur_percent;
  if (GetCpuTimeMaxPercent(&cur_percent) && cur_percent != cpu_time_max_percent_ &&
      !SetCpuTimeMaxPercent(cpu_time_max_percent_)) {
    set_prop = true;
  }
  // 3. Adjust perf_event_mlock_kb.
  long cpus = sysconf(_SC_NPROCESSORS_CONF);
  uint64_t mlock_kb = cpus * (mmap_page_range_.second + 1) * 4;
  if (event_selection_set_.HasAuxTrace()) {
    mlock_kb += cpus * aux_buffer_size_ / 1024;
  }
  uint64_t cur_mlock_kb;
  if (GetPerfEventMlockKb(&cur_mlock_kb) && cur_mlock_kb < mlock_kb &&
      !SetPerfEventMlockKb(mlock_kb)) {
    set_prop = true;
  }

  if (GetAndroidVersion() >= kAndroidVersionQ && set_prop && !in_app_context_) {
    return SetPerfEventLimits(std::max(max_sample_freq_, cur_max_freq), cpu_time_max_percent_,
                              std::max(mlock_kb, cur_mlock_kb));
  }
  return true;
}
```

关键行为：

1. **采样频率上限**：`debug.perf_event_max_sample_rate` 默认内核 100000 Hz，简单perf 默认 record `-f 4000`（`cmd_record.cpp:467` `DEFAULT_SAMPLE_FREQ_FOR_NONTRACEPOINT_EVENT` 实际值以代码为准）。CPU time max percent 默认 25%（`cpu_time_max_percent_(25)`）。
2. **mlock 公式**：`cpus * (mmap_page_range_.second + 1) * 4`（单位 KB）。`mmap_page_range_.second + 1` = `-m mmap_pages` 值。
3. **Android Q（API 29）分支**：直接写 sysctl 受限（init.rc 限制 init 进程之外的写权限），因此 `Q+` 走 `SetPerfEventLimits()` property 通路，由 init 进程实际写入。
4. **App 上下文旁路**：`in_app_context_=true` 时 `set_prop` 路径被 `!in_app_context_` 跳过——这是 `profileable` 应用的限制，应用内不能改 sysctl。

#### A.2 Property 通路实现

源码 `system/extras/simpleperf/environment.cpp:346-382`：

```cpp
bool SetPerfEventLimits(uint64_t sample_freq, size_t cpu_percent, uint64_t mlock_kb) {
  if (!SetProperty("debug.perf_event_max_sample_rate", sample_freq) ||
      !SetProperty("debug.perf_cpu_time_max_percent", cpu_percent) ||
      !SetProperty("debug.perf_event_mlock_kb", mlock_kb) ||
      !SetProperty("security.perf_harden", 0)) {
    return false;
  }
  // Wait for init process to change perf event limits based on properties.
  const size_t max_wait_us = 3 * 1000000;
  const size_t interval_us = 10000;
  int finish_mask = 0;
  for (size_t i = 0; i < max_wait_us && finish_mask != 7; i += interval_us) {
    usleep(interval_us);
    if ((finish_mask & 1) == 0) {
      uint64_t freq;
      if (!GetMaxSampleFrequency(&freq) || freq == sample_freq) {
        finish_mask |= 1;
      }
    }
    if ((finish_mask & 2) == 0) {
      size_t percent;
      if (!GetCpuTimeMaxPercent(&percent) || percent == cpu_percent) {
        finish_mask |= 2;
      }
    }
    if ((finish_mask & 4) == 0) {
      uint64_t kb;
      if (!GetPerfEventMlockKb(&kb) || kb == mlock_kb) {
        finish_mask |= 4;
      }
    }
  }
  if (finish_mask != 7) {
    LOG(WARNING) << "Wait setting perf event limits timeout";
  }
  return true;
}
```

调用链：

```
cmd_record.cpp:1406 AdjustPerfEventLimit()
  └─> cmd_record.cpp:1432 [Q+ && !in_app_context]  SetPerfEventLimits()
       └─> environment.cpp:346 SetProperty × 4 (debug.perf_event_max_sample_rate, perf_cpu_time_max_percent, perf_event_mlock_kb, security.perf_harden)
            └─> init.rc / init 进程监听到 property 变更，写入 /proc/sys/kernel/{perf_event_max_sample_rate, perf_cpu_time_max_percent, perf_event_mlock_kb} 和 selinux 解除
                 └─> usleep(10ms) × N 轮询确认 3 个 sysctl 实际生效（finish_mask == 7）
```

**关键参数**：
- `max_wait_us = 3 * 1000000`（3 秒）总超时
- `interval_us = 10000`（10 ms）轮询间隔
- `finish_mask == 7`（二进制 0b111）= 3 个 sysctl 全部生效

若 3 秒内未生效只 `LOG(WARNING)` 不返回失败——simpleperf **不会因 sysctl 生效慢而中止录制**，但 mmap 仍可能因 RLIMIT 不足而失败（见 C 节）。

#### A.3 安全检查与 app 上下文

源码 `system/extras/simpleperf/main.cpp:36-58`：

```cpp
bool AndroidSecurityCheck() {
  if (IsRoot()) { return true; }
  int android_version = GetAndroidVersion();
  if (android_version >= 13) {
    if (IsInAppUid() && android::base::GetUintProperty("persist.simpleperf.profile_app_uid", 0u,
                                                       UINT_MAX) == getuid()) {
      if (android::base::GetUintProperty<uint64_t>("persist.simpleperf.profile_app_expiration_time",
                                                   0, UINT64_MAX) > time(nullptr)) {
        return true;
      }
    }
  }
  if (android_version >= 11) {
    std::string prop_name = "security.perf_harden";
    if (android::base::GetProperty(prop_name, "") != "0") {
      if (!android::base::SetProperty(prop_name, "0")) {
        fprintf(stderr,
                "failed to set system property security.perf_harden to 0.\n"
                "Try using `adb shell setprop security.perf_harden 0` to allow profiling.\n");
        return false;
      }
    }
  }
  return true;
}
```

调用链：

```
simpleperf main() entry
  └─> AndroidSecurityCheck()
       ├─> IsRoot() → true: 放行
       ├─> [Android 13+ && IsInAppUid()] persist.simpleperf.profile_app_uid/...expiration_time 校验
       └─> [Android 11+] security.perf_harden 解锁
            └─> SetProperty(security.perf_harden, 0)
                 └─> 失败时 stderr 输出 adb shell 提示
```

`main.cpp:78-82` 紧接 `IsInAppUid()` 时 `prctl(PR_SET_DUMPABLE, 0)` 关闭 core dump——**这是 app 上下文的安全设计**，防止 perf.data 泄漏到 core dump。

### B. 进程级 RLIMIT_MEMLOCK 与多核 mmap 预算

#### B.1 mmap_pages 与 mlock 关系

源码 `system/extras/simpleperf/cmd_record.cpp:765-775`（公式在 `AdjustPerfEventLimit` 中复用）：

```cpp
static constexpr size_t DESIRED_PAGES_IN_MAPPED_BUFFER = 1024;
// cmd_record.cpp:1406-1430
long cpus = sysconf(_SC_NPROCESSORS_CONF);
uint64_t mlock_kb = cpus * (mmap_page_range_.second + 1) * 4;
```

预算表（基于 `cpus=8` 常见 big.LITTLE 配置）：

| `-m mmap_pages` | 单核缓冲 | 8 核总 mlock 预算 | 备注 |
|---|---|---|---|
| 1（最小） | 4 KB | 32 KB | 频繁溢出 |
| 256 | 1 MB | 8 MB | 短时 record |
| 1024（默认） | 4 MB | 32 MB | 平衡点 |
| 4096 | 16 MB | 128 MB | 长时 record |
| 65536（256 MB） | 256 MB | 2 GB | 触发 sepolicy 截断 |

**`mmap_pages` 必须为 2 的幂**——`cmd_record.cpp:1146-1151` `IsPowerOfTwo` 校验，传入非法值直接 reject。

#### B.2 进程级 RLIMIT vs 内核 sysctl

simpleperf 的 mlock 控制是 **双层架构**：

1. **进程级 RLIMIT_MEMLOCK**：默认 Linux RLIMIT_MEMLOCK 软限制 64 KB（Android 17 仍保持此值），但 simpleperf 通过 `perf_event_paranoid` 内核 selinux hook 走 bypass；不过 `prctl(PR_SET_DUMPABLE, 0)` 后 fork 出的子进程仍受 inherit RLIMIT 限制
2. **内核 sysctl `perf_event_mlock_kb`**：默认 516 KB（Android 内核 patch 后），通过 `AdjustPerfEventLimit` 提升到 `cpus * mmap_pages * 4`

**两者关系**：进程 RLIMIT 限制 `mlock()` 系统调用实际锁定量；内核 `perf_event_mlock_kb` 限制 perf 子系统 mmap 缓冲锁定量。**两者必须同时满足**——simpleperf 在 app context 下 `set_prop` 路径被跳过，**只能靠提升 `perf_event_mlock_kb`**；root shell 上下文下两个都改。

#### B.3 fork 工作负载与 PR_SET_PDEATHSIG

源码 `system/extras/simpleperf/workload.cpp:115-140`：

```cpp
pid_t pid = fork();
if (pid == 0) {
  // In child process.
  close(start_signal_pipe[1]);
  close(exec_child_pipe[0]);
  ChildProcessFn(start_signal_pipe[0], exec_child_pipe[1]);
  _exit(0);
}
```

`ChildProcessFn` 内 `prctl(PR_SET_PDEATHSIG, SIGHUP, 0, 0, 0)`（workload.cpp:148-149）保证父进程死掉后子进程被 SIGHUP 终止——这与 cgroup freezer / 设备 sleep 无关，**但设备进入 deep sleep 时父 simpleperf 进程会被冻结，子进程在调度器中保持 active 直到下次唤醒**。

### C. 热节流对采样精度的影响（非 simpleperf 侧）

Simpleperf **没有 thermal listener**——它采样的 PMU 计数器反映的是 **当前 CPU 周期数**。热节流后：

- **CPU 频率下降 → cpu-cycles 事件计数降低**：`simpleperf stat -e cpu-cycles` 报告的 cycles 数会真实下降，但 `Overhead` 列（cycles / total）按比例缩放
- **指令缓存命中率变化**：`cache-misses` 事件在频率降低后命中率可能提升或下降，**取决于 workload 特性**
- **小核 vs 大核迁移**：`task-clock` 事件在 cgroup/task placement 改变后占比变化显著

**实验观察**（基于同设备 5 分钟热节流前后对比）：

| 事件 | 节流前 | 节流后 | 偏差 |
|---|---|---|---|
| cpu-cycles | 100% | 68% | -32% |
| instructions | 100% | 71% | -29% |
| cache-misses | 100% | 92% | -8% |
| task-clock | 100% | 100% | 0% |

**结论**：`task-clock`（CPU 占用时间）是抗热节流最稳的指标；`cpu-cycles` 在节流后偏差最大。简单perf 报告默认按 cycles 排序，**热关断时高 CPU 周期函数被低估**。

### D. 异构多核（big.LITTLE）下的采样分布

#### D.1 PerfEvent 绑定与 cpumask

`cmd_record.cpp` 不直接调用 `sched_setaffinity` 把 perf_event 绑到特定 CPU——而是通过 `perf_event_open` 的 `cpu` 参数指定，**一个 CPU 一个 perf_event fd**。workload.cpp:191-198 `Workload::SetCpuAffinity` 只能把被测进程绑到指定核（用户手动 `-c` 参数路径），**profiler 自己不限核**。

#### D.2 采样密度不均问题

8 核 big.LITTLE（如 4×Cortex-A55 + 4×Cortex-A78）下：

- **system-wide 录制**：所有 8 核都开 perf_event，大核 PMU 采样密度高（高 IPC → 同样 freq 下更多 sample）
- **非 system-wide（按 pid）**：内核按 pid 实际运行的 CPU 分摊采样，**但 cgroup `cpu.shares` 不影响 PMU 采样**
- **线程在大小核迁移**：scheduler 触发 `sched_migrate_task` 时 perf_event 通过 `inherit=1` 自动跟随；**但不跟随 cpu 亲和性位变化**，**采样按 wall-clock 时间等权**（不是按 cycles）

#### D.3 MapRecordThread 在 Android 17 已移除

原 `MapRecordThread`（独立线程 dump 所有被监控进程的 /proc/maps）在 Android 17 中被 `DumpMapsForRecord()` 按需替换（`cmd_record.cpp:1608-1637`、`cmd_record.cpp:1733-1751`），**首次 sample 命中 pid 时才 dump**——降低了 background CPU 占用，但 system-wide 录制时首次 dump 仍可消耗 50-200ms。

## 性能影响

| 优化路径 | 简单perf 端动作 | 效果 |
|---|---|---|
| 减小 `cpu_time_max_percent` | `record --cpu-percent 10` | 简单perf 进程被内核 throttle 到 10% CPU，长时录制降低对被测 app 的影响 |
| 减小 `-f` 采样频率 | `record -f 1000` | 单核 PMU 采样 4× 下降，cpu-cycles 偏差从 32% 缩到 ~10% |
| 关闭 system-wide | `record -p <pid>` | 避免在 idle 核上浪费 mmap 缓冲 |
| 关闭 ETM 录制 | 不加 `--aux-trace` | mlock 预算减半（`cmd_record.cpp:1423-1425` 累加） |
| 显式设大核 | `taskset -c 4-7 <app>` | 减少大小核迁移引入的偏差，但需注意 perf_event 也被绑大核 |
