## 盲区来源

**关联章节**: `src/part2-performance/ch11-power/04-case-studies.md`（§11.4.1～§11.4.2 节流与 JobScheduler 案例集）

**原始盲区描述**: 每日推荐选题。章节在 §2.1 仅把 JobScheduler 的节流描述为「`JobConcurrencyManager` 根据 `maxActiveJobs` 和 `maxRunningJobs` 控制并发」，但未给出 Android 17 APEX 模块下 `JobSchedulerService` 的具体节流路径——尤其是「API 调用配额（API Quota）」、「执行时长配额（Runtime Free Quota）」、「Count Quota Tracker 滚动窗口算法」三套节流机制的具体源码位置、默认值与触发行为。同时章节也未把节流与电量优化（Batch / Prefetch / Connectivity Batching）之间的协同机制写清楚。本调研以 AOSP `android-17.0.0_r1` 源码为唯一一手资料，补齐以上断层。

**重要程度**: 中

## 核心发现

Android 17（API 37）的 JobScheduler 在 APEX 模块下把"节流"从单层并发控制演化为**五层叠加**：(1) **注册数节流**（`DEFAULT_MAX_JOBS_PER_APP=150`，即 `mMaxJobsPerApp`），限制单 app 持久化 Job 数量上限；(2) **API Quota 节流**（`DEFAULT_API_QUOTA_SCHEDULE_COUNT=250 / MINUTE_IN_MILLIS`，CountQuotaTracker 滑动窗口），限制 `schedule()` 调度频率；(3) **运行时长节流**（`DEFAULT_RUNTIME_MIN_GUARANTEE_MS=10min`、`DEFAULT_RUNTIME_FREE_QUOTA_MAX_LIMIT_MS=30min`），限制单 Job 最大执行窗口；(4) **并发控制**（`JobConcurrencyManager` 按 RAM 自适应 `DEFAULT_CONCURRENCY_LIMIT` 8/16/20/32/40），限制同时运行 Job 数量；(5) **强制批处理 / 唤醒合并**（`MIN_READY_CPU_ONLY_JOBS_COUNT` / `MAX_CPU_ONLY_JOB_BATCH_DELAY_MS=31min`），刻意延迟执行以合并多个 Job 到同一唤醒窗口。

这五层节流对应用的影响并非独立：API Quota 超限→应用被打入 STANDBY_BUCKET（`REASON_SUB_FORCED_SYSTEM_FLAG_BUGGY`）+ 抛 `LimitExceededException`（仅 debuggable app）+ 拒绝后续 schedule（`RESULT_FAILURE`）；Runtime Free Quota 用尽→Job 在 `mMinExecutionGuaranteeMs` 之后被 `shouldStopRunningJobLocked` 抢占（返回 `"too many jobs running"` / `"blocking BGUSER_IMPORTANT queue"` / `"battery saver"` 等 reason）。电量优化本质上是让多个 Job 共用一次 CPU 唤醒 + 一次 RIL/CONNECTIVITY 唤醒——`DEFAULT_MAX_CPU_ONLY_JOB_BATCH_DELAY_MS=31 * MINUTE_IN_MILLIS`（约半小时）是这一行为的硬编码上限。

源码版本：本文以 `android-17.0.0_r1` 标签下 AOSP 源码为准，对应 `frameworks/base/apex/jobscheduler/service/java/com/android/server/job/` 路径。

**CountQuotaTracker 核心算法**（`CountQuotaTracker.java:182-216`、`361-369`）：
```java
public boolean noteEvent(int userId, String packageName, String tag) {
    synchronized (mLock) {
        if (!isEnabledLocked() || isQuotaFreeLocked(userId, packageName)) return true;
        final long nowElapsed = mInjector.getElapsedRealtime();
        final LongArrayQueue times = mEventTimes
                .getOrCreate(userId, packageName, tag, mCreateLongArrayQueue);
        times.addLast(nowElapsed);
        final ExecutionStats stats = getExecutionStatsLocked(userId, packageName, tag);
        stats.countInWindow++;
        stats.expirationTimeElapsed = Math.min(stats.expirationTimeElapsed,
                nowElapsed + stats.windowSizeMs);
        if (stats.countInWindow == stats.countLimit) {
            final long windowEdgeElapsed = nowElapsed - stats.windowSizeMs;
            while (times.size() > 0 && times.peekFirst() < windowEdgeElapsed) {
                times.removeFirst();
            }
            stats.inQuotaTimeElapsed = times.peekFirst() + stats.windowSizeMs;
            postQuotaStatusChanged(userId, packageName, tag);
        }
        return isWithinQuotaLocked(stats);
    }
}

private boolean isUnderCountQuotaLocked(ExecutionStats stats) {
    return stats.countInWindow < stats.countLimit;
}
```

```java
            final long upperLimitMs = isWithinTimeoutQuota
                    ? mConstants.RUNTIME_UI_LIMIT_MS          // 12h
```

```java
public long getMaxJobExecutionTimeMs(JobStatus job) {
    synchronized (mLock) {
        if (job.shouldTreatAsUserInitiatedJob() && ... && mQuotaTracker.isWithinQuota(...)) {
            return mConstants.RUNTIME_UI_LIMIT_MS;   // 12h
        }
        if (job.shouldTreatAsUserInitiatedJob()) {
            return mConstants.RUNTIME_FREE_QUOTA_MAX_LIMIT_MS;  // 30min
        }
        final String timeoutTag = job.shouldTreatAsExpeditedJob()
                ? QUOTA_TRACKER_TIMEOUT_EJ_TAG : QUOTA_TRACKER_TIMEOUT_REG_TAG;
        final long normalUpperLimitMs = job.shouldTreatAsExpeditedJob()
                ? mConstants.RUNTIME_MIN_GUARANTEE_MS
                : mConstants.RUNTIME_FREE_QUOTA_MAX_LIMIT_MS;
        final long upperLimitMs =
                mQuotaTracker.isWithinQuota(job.getTimeoutBlameUserId(),
                        job.getTimeoutBlamePackageName(), timeoutTag)
                        ? normalUpperLimitMs
                        : mConstants.RUNTIME_MIN_GUARANTEE_MS;   // 10min（退化）
        return Math.min(upperLimitMs, mQuotaController.getMaxJobExecutionTimeMsLocked(job));
    }
}
```

### 5. 强制批处理：合并多次唤醒为一次

**位置**：`JobSchedulerService.java:784-790`（常量） + `JobSchedulerService.java:851-868`（字段） + `JobConcurrencyManager.java:1482-1512, 1684-1820`（触发条件）。

**常量定义**（`JobSchedulerService.java:784-790`）：

```java
private static final int DEFAULT_MIN_READY_NON_ACTIVE_JOBS_COUNT =
        Math.min(5, JobConcurrencyManager.DEFAULT_CONCURRENCY_LIMIT / 3);
private static final long DEFAULT_MAX_CPU_ONLY_JOB_BATCH_DELAY_MS = 31 * MINUTE_IN_MILLIS;
private static final long DEFAULT_MAX_NON_ACTIVE_JOB_BATCH_DELAY_MS = 31 * MINUTE_IN_MILLIS;
```

**字段**（`JobSchedulerService.java:851-868`）：
```java

int MIN_READY_NON_ACTIVE_JOBS_COUNT = DEFAULT_MIN_READY_NON_ACTIVE_JOBS_COUNT;
long MAX_CPU_ONLY_JOB_BATCH_DELAY_MS = DEFAULT_MAX_CPU_ONLY_JOB_BATCH_DELAY_MS;
long MAX_NON_ACTIVE_JOB_BATCH_DELAY_MS = DEFAULT_MAX_NON_ACTIVE_JOB_BATCH_DELAY_MS;
```

**调用链**：`JobConcurrencyManager.assignJobsToContextsLocked()` → `mUnbatchedJobs` 累积 → `shouldForceBatchLocked()` 决定是否延迟 → `MAX_*_BATCH_DELAY_MS` 决定最多等多久。

**关键细节**：
- `MAX_CPU_ONLY_JOB_BATCH_DELAY_MS = 31min` 意味着纯 CPU 类型的 Job（无 network 约束）系统**最多会延迟 31 分钟**才唤醒执行——目的是等待其他 app 也积累 ready Job 后一并执行。
- `MIN_READY_CPU_ONLY_JOBS_COUNT` 是触发批处理的条件：必须等 ready 数达到 `min(3, DEFAULT_CONCURRENCY_LIMIT/3)` 才唤醒（高端设备 3，中端设备 3，低端设备 1-2）。
- 网络 Job（`workType = WORK_TYPE_EJ`）有 `MIN_CONNECTIVITY_JOB_BATCH_DELAY_MS = 31min` + `CONN_TRANSPORT_BATCH_THRESHOLD`（CELLULAR 默认 3，WIFI/ETHERNET 不限）。
- 31 分钟这个数字对应：Doze maintenance window 默认 30min 一周期 + 1min buffer；过了窗口系统就强制唤醒执行。

```
  ├── [节流3] shouldStopRunningJobLocked() → 抢占旧 Job
  ├── [节流4] shouldForceBatchLocked() → 延迟 31min 等待批处理
  ↓
JobServiceContext.startJob() → scheduleOpTimeOutLocked()
  ↓
JobServiceContext.handleOpTimeoutLocked() (after mMaxExecutionTimeMillis)
  ├── [节流5] sendStopMessageLocked(reason="client timed out")
  ↓
JobSchedulerService.onJobCompletedLocked()
  ├── mQuotaTracker.noteEvent(QUOTA_TRACKER_TIMEOUT_*_TAG)  // Execution Safeguards
  ↓
如果 stop reason ∈ {TIMEOUT, ANR} 且次数超阈 → 下次 getMaxJobExecutionTimeMs 退化为 10min
```

## 性能影响

1. **API Quota 250/min 是经验值**——按 1Hz schedule 速率，4 分钟内即可打满。打满后：`schedule()` 不再返回 success（`API_QUOTA_SCHEDULE_RETURN_FAILURE_RESULT=false` 时仅 throw） + app 被强制 RARE bucket。开发者陷阱：在 onResume/onStartCommand 里 schedule 大量 Job 容易触发。

2. **批处理 31min 意味着首启延迟**：如果用户安装 app 后第一次 schedule 一个 CPU-only Job，理论上要等 `MIN_READY_CPU_ONLY_JOBS_COUNT` 个 ready Job 凑齐，最坏延迟 `MAX_CPU_ONLY_JOB_BATCH_DELAY_MS=31min`。OEM 测试时需关注首启 P95 延迟。

3. **`DEFAULT_RUNTIME_MIN_GUARANTEE_MS=10min` 决定抢占窗口**——被抢占的 Job 已经在前 10min 耗电。如果一个 app 周期 Job 1min 内被抢占（最小保证期后），实际开销 = 1min CPU + 1 次 wakeup —— 仍然没省电。OEM 在做"白名单节流"分析时，要按"实际执行时间 / 周期时间"衡量电量收益。

4. **Expedited Job 25 quota/15min（推算）**——`WorkInfo.getMinJobExecutionGuaranteeMs` 给 3min，但实际 `mQuotaController.getMaxJobExecutionTimeMsLocked()` 可能压更低；OEM 应监控 EJs 抢占率。

5. **应用打满 150 Job 后**——`countJobsForUid()` 遍历成本是 O(N)。Job 数量越多，schedule 越慢。这是 API Quota 之外的隐性反压。
