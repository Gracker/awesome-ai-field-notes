### 一、为什么我要重构我的写代码方式？

以前我写项目是这样的：

-   上来就让 ChatGPT / Cursor 写代码

-   没有任务分解，没有日志记录

-   有时候功能写一半就卡住

-   有时候 Cursor “自由发挥”，改了我根本没提过的部分

-   修 bug 修得很崩溃，写好的功能反而被破坏

> 最终写出来的代码能不能用，全靠运气。

所以我决定换一种方式：

✅ 从明确“要解决什么问题”开始
✅ 不直接写代码，而是先定义流程、结构、执行逻辑
✅ 把 AI 当作远程实习生，用文档和任务清单驱动它工作

* * *

#### ✅ Step 3：生成文档供 Cursor 使用（让GPT 写）

我用 prompt 让 GPT 一次性生成：

```markdown
按照前面讨论了的第一版mvp，请你帮我完成以下几件事：

1. 写出一份产品需求文档（prd.md）
2. 基于 PRD，生成一份工程结构和数据结构设计文档（erd.md）
3. 把 erd.md 中的模块拆解为任务清单，输出一份开发待办列表（todolist.md）
4. 最后打包成 zip 文件，方便我放进 Cursor 中开发
```

这些文档用来专门给 Cursor 使用：

-   prd.md：让它知道“整体要做什么”

-   erd.md：让它清楚“结构和数据长什么样”

-   todolist.md：一步步拆解为开发任务

* * *

✅ Step 4：Cursor 按清单开发，并写日志

接下去可以用Prompt 驱动 Cursor干活了：

```markdown
我是一个编程小白，我希望从零开始开发一个「通用 LLM Prompt 管理插件」，这是一个全新的 Chrome 插件项目。

请你阅读 `doc` 目录下的以下三个文档：
- `@prd.md`（产品需求文档）
- `@erd.md`（工程结构与数据结构设计）
- `@todolist.md`（开发任务清单）

你的任务是：
1. **严格按照 @todolist.md 中的顺序**，每次只执行一个待办任务（Todo），从插件结构搭建开始，逐步推进。
2. 每完成一个子任务，**在 @todolist.md 中勾选对应项**，并注明执行人/时间（可用注释）。
3. 每完成一个阶段，请说明你做了哪些修改（包含文件名、文件位置、代码逻辑、UI变动），并用注释或总结简洁说明。
4. 所有代码都必须加清晰注释，特别是变量和函数部分，方便我理解。
5. 不要提前做未列出的功能，不要重构已有内容，不要修改或删除 todolist 中的其他条目。
6. 如果遇到依赖未完成、结构不清等问题，可以跳过，但需要写清楚原因并在 todolist 中注明。

注意：
- 公共模版库文件已准备好，路径为：`public/prompts.json`，请直接使用。
- 不要一次做太多功能，每轮聚焦一个子模块，确保开发过程清晰、稳定、可追踪。

请开始开发，先从第一个 ToDo 项目启动，完成后更新 @todolist.md。
```

这里，GPT给了一个特别好的建议，是我以前没有想到的，就是每完成一个任务，就写一段结构化日志（非常关键）：

```markdown
你刚刚完成了一个 ToDo 开发任务，请将本次开发内容以日志的形式写入 doc目录下的 `cursor-log.md` 中。

日志格式如下：
---
## ✅ 功能名称：[从 todolist 中复制本项标题]

**完成时间**：自动填写为当前日期
**开发人**：Cursor

### 🔧 本次修改内容：
- 说明你新增了哪些功能、写了哪些逻辑
- 修改了哪些文件
- 如果有遇到问题，请写在这里

### 📁 涉及文件：
- [列出本次修改的所有文件]

### ✅ 实现效果：
- [功能最终是否实现？怎么测试的？]
---

请根据你刚才完成的 ToDo 项目内容，写一段符合上述格式的日志并追加到 `cursor-log.md` 文件末尾。

```

> **cursor-log.md + todolist.md 的组合，是这次“控住 AI”的最大抓手。**

这里的核心逻辑是：cursor-log.md = `todolist.md` 的“实际执行记录版本”

-   `todolist.md` 是 **计划清单**（要做什么）

-   `cursor-log.md` 是 **执行日志**（做了什么、怎么做的）

这个日志相当于让 Cursor 每完成一项 ToDo，就在 log 文件里「自动填写一段开发日记」，这样你能看得出：

> ✍️ 它到底改了哪些文件？写了什么功能？结构是否清晰？有没有踩坑？

进一步的，可以做的优化是：直接把这句加入 `todolist.md` 每条任务的注释，这样每次cursor自动看 ToDo 时就知道要写日志 ，可以自动完成了✅

```css
- [ ] 创建输入表单（提示词 + 描述 + 标签） ← 完成后：请写日志进 cursor-log.md
```

* * *

⚠️ Step 5：踩坑！Cursor 自作主张瞎改了存储方式

我注意到某一 ToDo 执行后，**cursor-log.md 没写、todolist 没勾**，我就发现不对了，生成了警觉（这个就是引入todolist.md和cursor-log.md 的又一个价值）。

果然，Cursor：

-   自作主张新增了「表单显示/隐藏 + 保存提示 + 清空表单」

-   把我原本用 `localStorage` 的逻辑换成了 `chrome.storage`

这导致我后续读取逻辑全错了，修改了几次bug才改回来。

🎯 解决方案：

-   在 todolist.md 中新增【AI建议任务区】

-   要求 Cursor 若认为某功能合理，必须：

-   写明理由

-   标记为 AI建议

-   不可私自加入功能分类

-   实际更新 `todolist.md 内容如下：`

```markdown
---

## 🧠 AI建议任务区（如新增逻辑、结构优化等）
> 说明：此区用于 AI 执行过程中主动建议新增的任务，需附上建议理由。
- [ ] （待补充）【AI建议】：例如新增 utils.js 工具模块，用于格式化 Prompt（请写明原因）

---

## 提醒：
- 所有任务必须严格按照顺序执行；
- 若认为需要新增任务，请先写入“AI建议任务区”，等待确认后再执行；
- 每个任务完成后请写入 cursor-log.md，对应修改打勾；

```

#### ✅ Step 6：生成 CHANGELOG.md + Git 封版

在功能全部跑通后，我先生成 changelog：

```markdown
你是一个经验丰富的技术文档助手。

请你根据以下三个信息源：
1. @todolist.md（任务清单，包含每个功能模块的开发项与状态）
2. @cursor-log.md（自动生成的 cursor 操作记录，包含每次修改的说明与代码变更摘要）
3. 当前的聊天记录上下文（包含我的反馈与变更请求）

为我输出一份格式规范的 `CHANGELOG.md`，内容包含以下结构：

---

## 版本号（如 v0.1.0）

### 🚀 新功能
- 简洁列出本次版本新增的核心功能（对应 todolist 中由 “❌” 变为 “✅” 的项）

### 🛠 修复与优化
- 根据 cursorlog.md 中的操作记录，归纳出修复了哪些问题，优化了哪些交互或逻辑

### 📁 文件与结构调整（如有）
- 记录文件结构的新增 / 删除 / 移动 / 重构（可选）

### 💬 备注说明
- 补充本次版本的一些特殊处理、遗留问题或下一步计划

---

请以清晰的 markdown 格式输出，适合直接保存为 `CHANGELOG.md`。
```

之后执行封版备份：

```cs
git init
git add .
git commit -m "v0.1"
```

📝 当然，建议在每一步核心功能开发完成后都做快照（git commit 一次），这样万一改坏可以随时回滚。

### 三、这次 AI 编程实践的完整流程

总结下优化后的整个流程：

1️⃣ 需求分析：7点讨论法（发散） + 三三原则（收敛）
2️⃣ 生成文档：prd.md / erd.md / todolist.md（供 Cursor 用）
3️⃣ Cursor 执行开发任务 1，严格按 todolist.md 开始
4️⃣ Cursor 执行开发任务 2～N，并持续写日志cursor-log.md
5️⃣ 监控执行偏差（日志缺失即预警）→ 及时修复
6️⃣ 全部跑通后 changelog 输出 + Git 封版归档

这不只是开发流程，更是一种「AI 协作方法论」的雏形。

之前的做法

现在的做法

❌ 直接让 Cursor 写代码，功能模糊、反复试错

✅ 先和 GPT 聊清楚需求，生成 `prd / erd / todolist` 三文档

❌ 写完才测试，改 bug 成为常态，甚至最终失败

✅ 每次只做一个核心功能，开发后立刻验证

❌ 没有日志机制，Cursor 有时“自由发挥”改坏结构

✅ 使用 `cursor-log.md` + `todolist.md` 追踪每一次执行

❌ Prompt 编写随意，缺乏约束性

✅ 由 GPT 帮我生成精细化 Prompt，控制流程更专业

❌ 多次失败后容易放弃

✅ 精简需求 + 提升可控性，大部分功能一次跑通
